# Nexaploy — Architecture & Contracts

Nexaploy is a Frappe/ERPNext hosting platform modelled after Frappe Cloud (Press).
Phase 0+1 delivers the server-side runtime: a per-server agent, a bench template
(Docker Compose), an image builder (one image per Release Group), and a proxy stack
(Traefik). The control plane (Frappe app, §8) talks only to the agent API described here.

This document is the **single source of truth** for paths, names and interfaces. Every
component MUST follow it so the parts fit together without negotiation. Repo paths below
are relative to the repository root (`bench-template/`, `image-builder/`, `agent/`,
`control-plane/`).

Two server models share **one code path**: *Hosted* (our VPS) and *BYOS* (Bring Your Own
Server — the customer runs `install.sh`, we charge a management fee). The only difference
is who pays for the VM.

## 1. Domain model (mirrors Press)

| Entity | Meaning | Lives in Phase 1 as |
|---|---|---|
| Marketplace App | A Frappe app (git URL) with versions; each version declares compatible Frappe majors (14/15/16) | `apps.json` entries |
| Release Group | Frappe major + exact app list/branches → produces images | `apps.json` + `frappe_branch` |
| Deploy Candidate | One built image of a Release Group | Docker image tag |
| Bench | A running instance of an image on one server (compose project) | `/opt/nexaploy/benches/<bench>/` |
| Site | A Frappe site inside a bench (own DB, own files, own domains) | `sites/<site>/` + Traefik router |
| Server | A host running the agent (ours or customer's BYOS) | the agent |

Rules:

- A server hosts many benches (v14, v15, v16 side by side). Each bench has its own image, Redis pair and compose project.
- A server has one shared MariaDB (`mariadb:11.8` LTS; the v16 image's 11.8 client requires TLS, which 11.4+ servers provide out of the box; 10.6 data dirs upgrade in place) used by all benches; each site gets its own database/user (standard Frappe).
- A bench hosts many sites. Traefik routes by Host and sets `X-Frappe-Site-Name: <site>` per site route; the bench frontend uses `FRAPPE_SITE_NAME_HEADER=$http_x_frappe_site_name`, so custom domains reach the right site.
- Moving a site to another major (v14 → v15) = backup → restore on a bench of the target Release Group → migrate. Never in place.

## 2. Filesystem layout on a server

```
/opt/nexaploy/

│   └── data/
│       └── jobs.db             # SQLite job store
├── config/
│   ├── agent.toml              # agent config (see §5.1)            mode 600
│   ├── db.env                  # DB_ROOT_PASSWORD=...               mode 600
│   ├── rclone.conf             # backup remote "nexaploy-backups"   mode 600
│   └── storage-rclone.conf     # attachment remotes nxs-<profile> (§11) mode 600
├── proxy/                      # Traefik stack (compose project "nexaploy-proxy")
│   ├── docker-compose.yml
│   ├── .env
│   ├── config/
│   │   ├── traefik/            # static middlewares (dynamic.yml)
│   │   └── sites/              # ONE file per site: <site>.yml (generated by agent)
│   ├── data/certificates/acme.json   (mode 600)
│   └── logs/
├── db/                         # shared MariaDB (compose project "nexaploy-db")
│   ├── docker-compose.yml
│   ├── .env
│   └── data/                   # /var/lib/mysql  (uid 3101)
├── images/
│   ├── frappe_docker/          # upstream clone (pinned), used as build context
│   ├── Containerfile           # Nexaploy parametrised Containerfile
│   ├── build.sh                # build entrypoint (see §4)
│   └── builds/<tag>/           # apps.json + build.log per build
├── benches/
│   └── <bench>/                # compose project name == <bench>
│       ├── docker-compose.yml  # rendered from template
│       ├── .env
│       ├── apps.json           # copy of the Release Group definition
│       ├── sites/              # bind mount -> /home/frappe/frappe-bench/sites (uid 3113)
│       └── logs/               # bind mount -> /home/frappe/frappe-bench/logs  (uid 3113)
├── backups/                    # staging area before rclone upload (uid 3113)
└── storage/                    # offloaded attachments (§11): state/<site>.json, cache/<site>/<kind>, logs/
```

Fixed UIDs/GIDs: frappe / bench containers **3113**, MariaDB **3101**, Redis **3102**, Traefik **3100**.

Docker networks:

- `proxy-network` (external, created by install): Traefik ↔ bench frontends.
- `nexaploy-db` (external, created by install): MariaDB ↔ bench backends/workers.
- `<bench>-net` (per bench, internal): backend ↔ redis ↔ websocket ↔ frontend.

Naming:

- Bench name: `^[a-z][a-z0-9-]{2,30}$` (e.g. `erp-v15-main`). Compose project = bench name.
- Site name: lowercase FQDN, `^(?=.{4,253}$)([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z]{2,63}$`. Slug = site with `.` → `-`.
- Container names: `<bench>-backend`, `<bench>-frontend`, `<bench>-websocket`, `<bench>-scheduler`, `<bench>-queue-short`, `<bench>-queue-long`, `<bench>-queue-default`, `<bench>-redis-cache`, `<bench>-redis-queue`.
- Shared containers: `nexaploy-db`, `nexaploy-traefik`.
- Image tag: `nexaploy/bench:<release_group>-<build_id>` (e.g. `nexaploy/bench:erp-v15-main-20261103T2130`).
  With a registry configured on the control plane (`Nexaploy Settings.registry_url`, e.g. `ghcr.io/org`)
  the tag is `<registry_url>/nexaploy/bench:<release_group>-<build_id>`; the build server pushes it and
  every other server pulls it (`docker login --password-stdin` first).

Deliverables in `bench-template/`:

```
bench-template/
├── bench/
│   ├── docker-compose.yml.j2   # Jinja2 template rendered by the agent
│   └── env.example
├── db/

│   └── env.example

│   ├── env.example
│   └── config/traefik/dynamic.yml      # middlewares: security-headers, rate-limit, compress

└── README.md
```

### 3.1 Bench compose variables (`.env` of a bench)

| Var | Example | Notes |
|---|---|---|
| `BENCH_NAME` | `erp-v15-main` | compose project name |
| `IMAGE` | `nexaploy/bench:erp-v15-main-20261103T2130` | |
| `FRAPPE_UID` / `FRAPPE_GID` | `3113` | |
| `REDIS_UID` / `REDIS_GID` | `3102` | |
| `TZ` | `Asia/Qatar` | |
| `DB_HOST` | `nexaploy-db` | shared DB container |
| `DB_PORT` | `3306` | |
| `BACKEND_WORKERS` | `2` | gunicorn workers |
| `BACKEND_CPUS` / `BACKEND_MEM` | `2` / `4G` | per-service limits; workers get smaller defaults |

The template must:

- Be hardened: `user:`, `tmpfs`, `security_opt: no-new-privileges`, resource limits, `logging: local`, healthchecks.
- Mount `./sites` and `./logs` (relative to the bench dir).
- Not include a DB (shared) and keep `redis-cache`/`redis-queue` per bench.
- Keep a `configurator` one-shot service that writes `common_site_config.json` (db_host, redis_*, socketio_port) idempotently — the agent runs it via `docker compose run --rm configurator`.
- NOT define Traefik labels on the frontend; routing is done by file provider (`site-route.yml.j2`), so a bench can serve many sites with distinct certs.
- Attach frontend to `proxy-network` and backend/workers/scheduler to `nexaploy-db`.

### 3.2 Site route template (`site-route.yml.j2`)

Variables: `site` (primary host), `domains` (list of all hosts incl. primary), `bench`.
Output file: `/opt/nexaploy/proxy/config/sites/<site>.yml` with router `site-<slug>` →
service `svc-<slug>` → `http://<bench>-frontend:8080`, `websecure` entrypoint,
`certResolver: letsencrypt`, middlewares `site-<slug>-name@file` (sets `X-Frappe-Site-Name`), `security-headers@file`, `compress@file`.

### 3.3 Proxy stack

Traefik v3, **file provider only** (no Docker provider, no docker socket): `providers.file.directory=/etc/traefik/dynamic` + `watch=true`, with `config/sites` mounted there flat (the file provider does not recurse); `install.sh` copies `config/traefik/dynamic.yml` into it as `_nexaploy-middlewares.yml` (the agent ignores names that are not site names). HTTP→HTTPS redirect to the public port, ACME HTTP challenge, JSON access log, Prometheus metrics, healthcheck. CrowdSec optional (`COMPOSE_PROFILES=crowdsec`).

### 3.4 Shared DB stack

`mariadb:11.8` (override with `MARIADB_IMAGE`), utf8mb4, `--skip-innodb-read-only-compressed`,
`--innodb-buffer-pool-size=${DB_BUFFER_POOL:-1G}`, healthcheck, bind mount `./data`,
network `nexaploy-db`, no published ports. Root password from `/opt/nexaploy/config/db.env` (`env_file`).

## 4. Image builder (component B)

Deliverables in `image-builder/`:

```
image-builder/
├── Containerfile          # parametrised multi-stage build (base → builder → backend)
├── build.sh
├── versions.json          # defaults per Frappe major
├── examples/
│   ├── apps-v14.json
│   ├── apps-v15.json
│   └── apps-v16.json
└── README.md
```

`versions.json` (overridable by flags):

```json
{
  "14": {"python": "3.10.13", "node": "16.20.2", "frappe_branch": "version-14", "debian": "bookworm"},
  "15": {"python": "3.11.6",  "node": "18.20.2", "frappe_branch": "version-15", "debian": "bookworm"},
  "16": {"python": "3.14.10", "node": "24.22.2", "frappe_branch": "version-16", "debian": "trixie"}
}
```

(v16 requires Python >=3.14,<3.15 and Node >=24 — verified against frappe `version-16` pyproject/package.json on 2026-11-03.)

`build.sh` contract:

```
build.sh --major 15 --apps-json /path/apps.json --tag nexaploy/bench:erp-v15-main-20261103T2130 \
         [--frappe-branch version-15] [--python 3.11.6] [--node 18.20.2] \
         [--context /opt/nexaploy/images/frappe_docker] [--push] [--log /path/build.log]
```

- Exit 0 on success; prints the final tag on the last stdout line.
- Pass apps.json as `APPS_JSON_BASE64`; nginx template/entrypoint come from the upstream frappe_docker context (`resources/` paths kept).
- Resulting image runs as UID 3113 (`frappe`), includes rclone, restic, mariadb-client, wait-for-it, jq, CMD = gunicorn, ships `nginx-entrypoint.sh`.
- The image ENTRYPOINT `nexaploy-entrypoint.sh` symlinks `sites/assets` → baked `/home/frappe/frappe-bench/assets` and refreshes `sites/apps.txt` on each start (the `./sites` bind mount hides them). Compose files must not override `entrypoint:` on long-running services.
- apps.json must not list frappe itself (installed via `--frappe-branch`).
- Apps in apps.json are `{url, branch}` objects; private repos via `https://<token>@github.com/...` are the caller's responsibility.

### 5.1 agent.toml

```toml
[agent]
server_id = "srv-ab12"           # assigned by control plane or generated
token = "..."                    # bearer token for the local API
bind = "127.0.0.1"               # set 0.0.0.0 only behind TLS
port = 8787
root = "/opt/nexaploy"

[control_plane]
url = ""                         # empty => standalone mode
token = ""                       # server token issued by control plane
heartbeat_seconds = 60
poll_seconds = 10

[backup]
remote = "nexaploy-backups"      # rclone remote name
prefix = "srv-ab12"              # path prefix inside the remote
retention_days = 14
```

### 5.2 REST API (all under `/v1`, `Authorization: Bearer <token>`)

| Method | Path | Body / effect |
|---|---|---|
| GET | `/v1/ping` | `{ok, version, server_id}` |
| GET | `/v1/server` | host facts |
| GET | `/v1/jobs`, `/v1/jobs/{id}` | job with steps + output |
| POST | `/v1/server/health` | job `server.health` (result = host facts, same as the heartbeat) |
| POST | `/v1/server/backup-config` | `{remote, type: s3, provider, endpoint, region, bucket, access_key_id, secret_access_key, prefix}` → job `server.configure_backups` (writes `config/rclone.conf` mode 600 + `[backup]` in agent.toml; idempotent) |
| POST | `/v1/images/build` | `{major, apps_json, tag, frappe_branch?, push?, registry?: {url, username, password}}` → job `image.build` (`docker login --password-stdin` before pushing) |
| GET | `/v1/benches` | list |
| POST | `/v1/benches` | `{name, image, env?, apps_json?, registry?}` → job `bench.create` (render compose, login + pull if needed, up, run configurator) |
| POST | `/v1/benches/{b}/start` / `stop` / `restart` | job `bench.start` / `bench.stop` / `bench.restart` |
| POST | `/v1/benches/{b}/update` | `{image, registry?}` → job `bench.update` (up with new image, migrate all sites) |
| DELETE | `/v1/benches/{b}` | job `bench.remove` (refuses if sites exist unless `force`) |
| GET | `/v1/benches/{b}/sites` | list |
| POST | `/v1/benches/{b}/sites` | `{name, admin_password, apps:[...]}` → job `site.create` (new-site, install apps, enable Frappe monitor `set-config -p monitor 1`, write route) |
| POST | `/v1/sites/{s}/apps` | `{app}` → job `site.install_app` |
| DELETE | `/v1/sites/{s}/apps/{app}` | job `site.uninstall_app` |
| POST | `/v1/sites/{s}/domains` | `{domain}` → job `site.add_domain` (route rewrite + add-domain) |
| DELETE | `/v1/sites/{s}/domains/{d}` | job `site.remove_domain` |
| POST | `/v1/sites/{s}/backup` | `{with_files: true, upload: true}` → job `site.backup` (result adds `backup_files:[{file_type: database\|public\|private\|site_config, name, size, sha256, remote_key}]`; `remote_key` = object key in the bucket) |
| GET | `/v1/sites/{s}/backups` | list local + remote |
| POST | `/v1/sites/{s}/backups/prune-remote` | `{bench?, keep_days=14, keep_min=3, prefix?}` → job `backup.prune_remote` (`rclone lsf` the dated dirs, `rclone purge` those older than `keep_days`, never the newest `keep_min`) |
| POST | `/v1/sites/{s}/restore` | `{backup_id}` or `{remote_path}` → job `site.restore` |
| POST | `/v1/sites/{s}/migrate` | job `site.migrate` |
| POST | `/v1/sites/{s}/config` | `{key, value}` → job `site.set_config` |
| GET | `/v1/sites/{s}/config` | site_config.json, secrets redacted (`db_password`, `encryption_key`, keys matching `password\|secret\|token\|key`); the CP uses job `site.get_config` `{site}` (same result) |
| PATCH | `/v1/sites/{s}/config` | `{set: {k: json}, remove: [k]}` → job `site.update_config` (one atomic rewrite of site_config.json; `db_*`/`encryption_key` refused) |
| POST | `/v1/usage` | `{bench?, site?, ensure_monitor?, refresh_sizes?}` → job `site.usage` (per-site CPU/request time, DB size, file storage; result `{sites, usage}`) |
| DELETE | `/v1/sites/{s}` | job `site.drop` (backup first unless `skip_backup`) |

The agent resolves which bench a site belongs to by scanning `benches/*/sites/<s>/site_config.json`.
Every mutating call returns `202 {job_id}`. Jobs run serially on the worker (one job at a
time per server). The job `kind` strings above are also what the control plane sends.

### 5.3 Job model

```
Job:  id (ulid), kind, params(json), status: queued|running|success|failure|cancelled,
      created_at, started_at, ended_at, error, origin (local|control_plane), remote_id
Step: job_id, idx, name, status: pending|running|success|failure|skipped,
      output(text, appended), started_at, ended_at
```

Each job class declares an ordered list of steps; each step is idempotent (check-then-act).
On failure the job stops, remaining steps are skipped, and the API exposes the full output.
Params keys matching `password|secret|token|key` are redacted in API output and logs (at any
depth, e.g. `registry.password`). Registry passwords only ever reach `docker login` via stdin.

### 5.4 Site operations are executed inside the bench

All `bench ...` commands run as
`docker compose -p <bench> --project-directory /opt/nexaploy/benches/<bench> exec -T backend bench ...`
(or `run --rm backend` when the stack is down). Never on the host. Commands are argument
lists (no `shell=True`); names are validated against §2 regexes first.

### 5.5 Backups

- `bench --site <s> backup --with-files` → files in `sites/<s>/private/backups/`.
- Agent moves them to `/opt/nexaploy/backups/<bench>/<s>/<ts>/`, writes `manifest.json`
  (`{site, bench, image, created_at, files:[{name,size,sha256}]}`) and (if upload)
  `rclone copy` to `<remote>:<prefix>/<bench>/<s>/<ts>/`, then prunes local beyond retention.
- Restore: fetch (rclone) if needed, verify sha256, `bench --site <s> restore <sql.gz> --with-public-files ... --with-private-files ... --db-root-password ...`, then `bench --site <s> migrate`.

### 5.6 Control plane protocol

Outbound only. If `control_plane.url` is set the agent (header `Authorization: token <control_plane.token>`):

- `POST {url}/api/method/nexaploy.api.agent.heartbeat` body `{server_id, facts, benches, agent_version[, usage]}` every `heartbeat_seconds`.
  `usage` (at most every 15 min, agent-side throttle) = `{collected_at, date, sites: {site: {database_mb, storage_mb,
  days: {YYYY-MM-DD: {cpu_seconds, requests}}}}}` for today and yesterday (UTC). CPU = sum of Frappe monitor
  `duration` (µs) of `request`/`job` transactions read incrementally from `benches/<b>/logs/monitor.json.log`
  (offset/inode in `agent/data/usage_state.json`); DB size from `information_schema` via
  `docker exec -e MYSQL_PWD nexaploy-db mariadb -uroot` (password only in the env); storage = `du -sb` of
  `sites/<s>/{public,private}/files` (cached 1 h). The CP upserts one **Site Usage** row per site per UTC day.
  `facts` include `cpu_count`, `load_avg`, `mem_total/mem_available/mem_used`, `mounts`
  (`[{path, total, used, free, used_percent}]` for `/` and `/opt/nexaploy`), `containers`
  (Nexaploy containers: `{name, project, service, state, health}`), `bench_health`
  (`{bench: {total, running, unhealthy:[names], healthy}}`), `unhealthy_containers` and
  `utc_offset_minutes` (server-local time for update windows).
- `GET {url}/api/method/nexaploy.api.agent.poll?server_id=` every `poll_seconds` → `{"message": [{job_id, kind, params}, ...]}`; each item is enqueued locally (`origin=control_plane`, `remote_id=job_id`).
- `POST {url}/api/method/nexaploy.api.agent.job_update` body `{server_id, job_id, status, steps:[{idx,name,status,output,started_at,ended_at}], error, result}` on every status/step change.
- Registration (BYOS): `POST {url}/api/method/nexaploy.api.agent.register` body `{registration_token, hostname, facts, agent_version}` → `{"message": {server_id, server_token}}`. Called once by `install.sh` when `--token` is a registration token.

Retries with exponential backoff; the agent keeps working standalone if the CP is down.

### 5.7 install.sh

Idempotent, Ubuntu 22.04/24.04 (Debian 12 best effort), run as root:

1. Preflight: arch, RAM ≥ 2 GB, disk ≥ 20 GB, ports 80/443 free.
2. Install Docker CE + compose plugin (official repo), git, python3-venv, rclone, jq, acl.
3. Create users/groups with fixed UIDs (3100 traefik, 3101 mariadb, 3102 redis, 3113 frappe) and the `/opt/nexaploy` tree with ownership per §2.
4. Create networks `proxy-network`, `nexaploy-db`.
5. Install agent (git clone or local path), venv, `pip install .`.
6. Write `agent.toml` from flags (`--token`, `--control-plane`, `--server-id`, `--acme-email`), generate `db.env`; register with the CP if a URL + token were given.
7. Install + enable systemd units; start proxy + db stacks.
8. Print summary and `nexaploy ping` result.

Uninstalling the agent leaves benches and sites running — **no lock-in**.

## 6. Non-goals for Phase 1

Billing, marketplace UI, multi-server scheduling, site migration between servers,
monitoring dashboards. These live in the control plane (Phase 2+).

## 7. Testing expectations (no Docker on dev machines)

- Agent: pytest with the docker runner mocked; cover job store, step idempotency, compose rendering, route rendering, backup path logic, API auth,
  registry login via stdin + redaction, `rclone.conf` rendering (mode 600, idempotent), remote retention selection, container health facts.
- Control plane: pure logic in `nexaploy/utils.py` and `nexaploy/ops_utils.py` (no frappe import) with plain pytest; DocType JSON checked statically.
- Templates: render with Jinja2 in tests and parse YAML to assert structure (service names, networks, mounts, UIDs).
- Shell scripts: `bash -n`; keep them simple.

## 11. Offsite attachments, DR replica, trash bin (paid add-ons)

Customer attachments (`sites/<s>/{public,private}/files`) can live on any S3-compatible object
storage (AWS S3, iDrive e2, Wasabi, Backblaze B2, Cloudflare R2, MinIO, Hetzner Object Storage,
other), optionally replicated to a bucket in another region, with deleted files kept in a third
"trash" bucket for a retention period. The server keeps only a bounded cache.

### 11.1 Design choice: per-site `rclone mount` on the host

Options considered:

| | (a) rclone mount (chosen) | (b) Frappe app storing File docs on S3 | (c) periodic `rclone move` + proxy fallback |
|---|---|---|---|
| Frappe compatibility | Full POSIX: `File.get_content()`, PDFs/print images, Data Import, email attachments, `is_safe_path` all work unchanged | Only code paths the app patches; third-party apps reading `get_full_path()` break; file URLs change | Moved files are gone from disk: `get_content()`, imports, attachments in emails, PDF rendering fail for old files |
| Private files | Frappe's own permission check + X-Accel-Redirect, unchanged | App's download endpoint | nginx cannot SigV4-sign; needs a signing sidecar behind `/protected/` |
| Images / apps | none (host-level) | app in every image (also customer BYOS/custom images), migrations per Frappe major | custom nginx template in every image |
| Providers | every rclone S3 provider | boto3-compatible; per-app quirks | every rclone provider |
| Host requirements | FUSE (`fuse3`), shared mount propagation, rclone ≥ 1.62 | none | none |
| Failure mode | mount down → uploads fail loudly (root-owned empty mountpoint), reads 404; systemd restarts it | S3 down → uploads fail | S3 down → old files 404 |

(a) is the most robust for *Frappe correctness* — the site sees a normal directory — and keeps all
moving parts on the host, managed by the agent. Its operational risks are mitigated:

- **Mount propagation.** One `rclone mount` per site and kind (`public`, `private`) runs as a systemd unit
  (`/etc/systemd/system/nexaploy-files-<slug>-<kind>.service`, `Type=notify`, `Restart=always`,
  `Before=docker.service`, `ExecStartPre/ExecStopPost=fusermount3 -uz`) and mounts **directly on**
  `benches/<b>/sites/<s>/<kind>/files` (no symlinks: Frappe's path checks and nginx `try_files` see a real dir).
  The bench `./sites` bind mount uses `${SITES_PROPAGATION:-rprivate}`; the agent sets `SITES_PROPAGATION=rslave`
  in the bench `.env` (re-render + `up -d`, once) so containers follow mounts that appear, restart or fail over
  later. Docker's `rslave` needs the host path on a shared mount (systemd default for `/`); the agent checks
  `findmnt -o PROPAGATION` first and refuses otherwise (`mount --make-rshared /` at boot fixes it).
- **Mount down.** The mountpoint underneath is an empty root-owned `0755` dir: Frappe (uid 3113) cannot write
  to it, so a dead mount never silently fills the server's disk with files the bucket does not have.
- **Write safety.** `--vfs-cache-mode full` acknowledges writes locally and uploads after `--vfs-write-back 5s`;
  dirty files survive crashes/reboots in `storage/cache/<s>/<kind>` and are uploaded on the next start. Before
  unmounting for good (`to_local`, drop) the agent waits until rclone's VFS metadata has no `"Dirty": true`
  item (restarting the mount to flush late writes); it refuses to remove a unit with pending uploads.
- **Bounded disk.** `--vfs-cache-max-size` (Storage Settings `cache_max_size`, default 2G per mount),
  `--vfs-cache-max-age 72h`. `--allow-other --uid 3113 --gid 3113 --umask 0027`, `--dir-cache-time 5m`,
  `--poll-interval 0` (S3 has no change notifications; the agent sends `SIGHUP` to flush the directory cache
  after server-side changes such as a trash restore).
- **Backups** of an offloaded site are database-only (tarring the mount would download the whole bucket; the
  files are already off-server and replicated). `du` for usage skips mountpoints.
- **Rename** of an offloaded site is refused by the agent (move the files back first). **Drop** unmounts and
  removes the units first; bucket data is kept. **Move** to another server restores the DB-only backup; the
  control plane notices the new server (`Site Storage Policy.server`) and re-runs `site.storage_migrate`
  there, which finds an empty local dir and just mounts the bucket.

Host requirements (install.sh): `fuse3` (for `fusermount3`), rclone ≥ 1.62 from rclone.org (Ubuntu 22.04's
1.53 lacks the IDrive/Cloudflare providers and some VFS fixes), `user_allow_other` is not needed (mounts run
as root). Each mount costs ~30–60 MB RAM.

### 11.2 Bucket layout and replication semantics

```
<primary>/<prefix>/<site>/{public,private}/...                 live files (Frappe writes through the mount)
<replica>/<prefix>/<site>/{public,private}/...                 copy, synced every N minutes
<replica>/<prefix>/.nexaploy-trash-staging/<site>/<ts>/...      transient --backup-dir (other account only)
<trash>/<prefix>/<site>/<ts>/{public,private}/...              deleted/overwritten files, pruned by age
```

`server.storage_replicate` runs, per site and kind,
`rclone sync primary:<site>/<kind> replica:<site>/<kind> --backup-dir <B>/<kind> --max-delete N --fast-list --size-only`.
A file Frappe deletes is removed from the primary at once (through the mount); at the next sync it still
exists in the replica, and `--backup-dir` **moves** it out of the replica instead of deleting it — so deleted
files end up removed from primary and replica and kept in the trash (overwritten files too). rclone requires
`--backup-dir` on the same remote as the destination: when the trash profile is in the same account as the
replica (same provider/endpoint/region/key) `B` is the trash bucket addressed through the replica's remote
(server-side move); otherwise `B` is a staging dir in the replica bucket outside `<prefix>/<site>` and the job
then `rclone move`s it to the trash. Limits and guards:

- Files created **and** deleted between two syncs never reach the replica, so they are not in the trash (RPO =
  interval, default 15 min). Bucket versioning on the primary closes that gap if the provider offers it.
- `--max-delete` (default 1000) stops a runaway sync; a sync whose primary dir is missing while the replica has
  files is refused (a mis-pointed primary must not empty the replica).
- Sites that are failed over (mounted on the replica), migrating, or not yet offloaded are never synced; one
  failing site does not stop the others (per-site result, job fails at the end).
- `--size-only` avoids a HEAD per object across providers (Storage Settings `replication_compare` can switch to
  `modtime` or `checksum`).

`server.storage_prune_trash` (daily): `rclone delete trash:<site> --min-age <days>d --rmdirs`.
`site.storage_trash_list` / `site.storage_trash_restore` (`<ts>[/<kind>[/<path>]]`, copied with
`copyto`/`copy` into the currently served bucket, kept in the trash until pruned).

**Failover** (`site.storage_failover {target: replica}`): rewrite the units to the replica and restart (brief
interruption; replication pauses). Files written since the last sync are not on the replica; pending uploads to
the dead primary stay in the cache. **Failback** (`target: primary`): `rclone sync replica -> primary` with the
same trash capture (files deleted during the failover go to the trash), then remount the primary.
