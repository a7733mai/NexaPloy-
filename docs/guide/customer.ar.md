# دليل العميل

هذا الدليل موجّه إلى **عملاء** منصة Nexaploy: تشغّل مواقع Frappe / ERPNext على الاستضافة المشتركة
للمنصة، أو على خادم تنشئه لك المنصة، أو على **خادمك الخاص** (BYOS). كل شيء يتم من لوحة التحكم على
`https://<platform>/dashboard`. أما أصحاب المنصة فيقرؤون [دليل المشغّل](operator.md).

لوحة التحكم متاحة بالعربية والإنجليزية. غيّر اللغة من **الحساب ← اللغة** (العربية تُعرض من اليمين إلى
اليسار).

!!! tip "عن أسماء الأزرار"
    نكتب اسم الزر كما يظهر في الواجهة العربية، ويليه أحيانًا الاسم الإنجليزي بين قوسين حتى تجده
    مهما كانت لغة الواجهة.

## 1. التسجيل والدخول

هناك طريقتان للحصول على حساب:

- **التسجيل الذاتي في منتج** (مثل ERPNext): افتح رابط التسجيل الذي تعطيك إياه المنصة
  (`/signup/<product>`)، وأدخل الاسم الكامل والبريد والشركة (اختياري) وعنوان الموقع وكلمة المرور، ثم
  اضغط **أنشئ موقعي** (Create my site). أكّد الرابط المرسل إلى بريدك. يُنشأ موقعك خلال دقائق؛ ادخل
  إليه باسم `Administrator` وبكلمة المرور التي اخترتها. التجربة مجانية للمدة المعروضة وبلا بطاقة.
- **دعوة** من فريق موجود (انظر أدناه)، أو حساب ينشئه لك المشغّل.

عند أول استخدام تحصل على فريق شخصي. ادخل من `https://<platform>/login`.

## 2. الفرق والأدوار والأمان

كل شيء (الخوادم والمواقع والنسخ والفواتير) يتبع **فريقًا**. بدّل بين الفرق من القائمة الجانبية، وأنشئ
فريقًا آخر من **الفريق ← فريق جديد**.

| الدور | ما يمكنه فعله |
|---|---|
| **المالك** (Owner) | كل شيء، بما في ذلك إدارة المالكين الآخرين |
| **مسؤول** (Admin) | الأعضاء والدعوات والخوادم ومفاتيح API والفوترة والمواقع |
| **مطوّر** (Developer) | المواقع ومجموعات البنش والتطبيقات والنسخ الاحتياطية والنطاقات والإعدادات |
| **الفوترة** (Billing) | الفواتير والمدفوعات والخطط والرصيد |

الجميع يستطيع العرض. لا يدعو أو يزيل مالكًا إلا مالك، ويبقى في الفريق مالك واحد على الأقل دائمًا.

### دعوة عضو

1. **الفريق ← الدعوات**: أدخل *البريد الإلكتروني* واختر الدور ثم **دعوة**.
2. يفتح المدعو الرابط المرسل (صالح 7 أيام) ويضغط **قبول الدعوة** وهو مسجّل الدخول بالبريد نفسه. إذا
   تعذّر إرسال البريد، انسخ الرابط الظاهر وأرسله له.
3. غيّر الدور أو **إزالة** العضو من قائمة **الأعضاء**، و**إلغاء** دعوة معلّقة.

### المصادقة الثنائية (2FA)

- المالك/المسؤول: **الفريق ← الأمان ← فرض المصادقة الثنائية على جميع الأعضاء**. يُطلب من الأعضاء رمز
  لمرة واحدة من تطبيق مصادقة عند تسجيل الدخول **التالي**.
- **الحساب ← المصادقة الثنائية** يعرض حالتك أنت.
- مفاتيح API لا تستخدم المصادقة الثنائية، فاحفظها بسرية.

### الحساب ومفاتيح API

في **الحساب**: الملف الشخصي، واللغة، و**تغيير كلمة المرور**، و**الوصول عبر واجهة البرمجة**:
**إنشاء مفتاح API** يعرض السر **مرة واحدة فقط**، و**تدوير** يصدر زوجًا جديدًا، و**إلغاء** يحذفه.

```bash
curl -s https://<platform>/api/method/nexaploy.api.dashboard.list_sites \
  -H "Authorization: token <api_key>:<api_secret>" \
  -H "X-Nexaploy-Team: <team>"
```

### سجل النشاط

**النشاط** (للمالك والمسؤول) يسرد كل تغيير في الفريق: من، وماذا، ومتى، ومن أي عنوان IP. يمكن التصفية
حسب الإجراء والعضو والتاريخ. لا يمكن تعديله أو حذفه.

## 3. أين تعمل مواقعك

| الخيار | ماذا تدفع | من يدير الخادم |
|---|---|---|
| **استضافة مشتركة** | خطة موقع لكل موقع | المنصة |
| **خادم مستضاف** (**الخوادم ← إنشاء خادم مستضاف**) | خطة خادم | المنصة تنشئه على Hetzner/DigitalOcean، وهو لك وحدك |
| **خادمك الخاص (BYOS)** | رسوم إدارة لكل خادم، وتدفع ثمن الخادم لمزوّدك | أنت تملكه، وNexaploy تدير البنشات والمواقع |

### إنشاء خادم مستضاف

1. **الخوادم ← إنشاء خادم مستضاف**.
2. اختر المزوّد والمنطقة وحجم الخادم، واسمًا للخادم اختياريًا. يظهر السعر الشهري.
3. **إنشاء الخادم**. يستغرق التجهيز 5–10 دقائق، ثم **فتح الخادم**.

### أضف خادمك الخاص (BYOS)

تحتاج خادم **Ubuntu 22.04 أو 24.04** جديدًا (x86_64 أو arm64)، بذاكرة 2 جيجابايت على الأقل (يُنصح بـ 4
أو أكثر)، و20 جيجابايت فارغة، والمنفذين **80 و443** مفتوحين للإنترنت.

1. **الخوادم ← أضف خادمك الخاص ← إنشاء أمر التثبيت**.
2. ادخل إلى خادمك وشغّل الأمر الظاهر بصلاحيات root:

    ```bash
    curl -fsSL https://<platform>/install.sh | sudo bash -s -- \
      --token <registration-token> --control-plane https://<platform>
    ```

3. تابع الصفحة: "بانتظار تسجيل خادمك…" ← "تم تسجيل الخادم، بانتظار أول نبضة…" ← "خادمك متصل ونشط".
4. الرمز يُستخدم مرة واحدة وتنتهي صلاحيته (24 ساعة). إذا انتهت فاضغط **إنشاء أمر جديد**.

!!! note "المثبّت يحدّث نظام التشغيل أولًا"
    قبل تثبيت أي شيء ينفّذ `install.sh` ترقية كاملة للنظام (`apt-get update` ثم `apt-get full-upgrade`
    مع الإبقاء على ملفات إعدادك، ثم `autoremove`)، وهذا يثبّت أحدث نواة أيضًا. إذا احتاج الأمر إعادة
    تشغيل، يكمل المثبّت التثبيت ثم **يعيد تشغيل الخادم تلقائيًا بعد دقيقة واحدة** (وفي الوضع التفاعلي
    يسألك أولًا). تعود مواقعك تلقائيًا بعد إعادة التشغيل.

    | الخيار | الأثر |
    |---|---|
    | `--no-os-upgrade` | تخطي ترقية النظام |
    | `--hwe-kernel` | Ubuntu: تثبيت نواة HWE الأحدث أيضًا |
    | `--no-reboot` | عدم إعادة التشغيل تلقائيًا؛ أعد التشغيل بنفسك لاحقًا |
    | `--acme-email you@example.com` | بريد شهادات Let's Encrypt (موصى به) |

المنصة لا تحتاج SSH ولا منافذ مفتوحة على خادمك: الوكيل هو من يتصل للخارج. وإذا أزلت الوكيل
(`systemctl disable --now nexaploy-agent-api nexaploy-agent-worker`) تبقى مواقعك تعمل.

### صفحة خادمك

افتح الخادم من **الخوادم** لترى حالته، وآخر نبضة، وإصدار الوكيل، ومعلومات الخادم، والبنشات، وآخر المهام.
الخادم الذي لم يرسل نبضة منذ 5 دقائق يظهر *غير متصل*: تأكد أنه يعمل وأن خدمات `nexaploy-agent` نشطة.
تظهر على خوادمك **شارة صحة** (OK أو Warning أو Critical أو Unknown أو Offline) مع المشكلات المكتشفة
وتلميح لكل منها.

إذا سمحت المنصة، يستطيع المالك والمسؤول أيضًا **ترقية الوكيل** / **استرجاع إصدار الوكيل السابق** على
خوادمهم.

### تحديثات النظام على خادمك الخاص

يرى المالك والمسؤول بطاقة **تحديثات النظام** (System updates) على خوادم BYOS الخاصة بهم:

- التحديثات المعلّقة وكم منها أمنية؛
- النواة العاملة وأحدث نواة مثبتة، وعبارة **يلزم إعادة التشغيل** (Reboot required) عند الحاجة؛
- **حدّث الآن** (Update now): كل التحديثات أو الأمنية فقط، مع إعادة التشغيل *أبدًا* أو *عند الحاجة*؛
- **أعد التشغيل الآن** (Reboot now)؛
- **نافذة الصيانة** (Maintenance window): يوم وساعة أسبوعيًا (بتوقيت UTC) للتحديثات، مع إعادة تشغيل
  تلقائية عند الحاجة؛
- **التحديثات الأمنية التلقائية** (Automatic security updates): تثبّت التحديثات الأمنية يوميًا ولا تعيد
  التشغيل من تلقاء نفسها أبدًا.

لا تحدث إعادة التشغيل إلا بعد أن تبلّغ المهمة بالنجاح. تتوقف مواقعك لحظات أثناء إعادة التشغيل ثم تعود
تلقائيًا.

## 4. مجموعات البنش وإصدارات Frappe

**مجموعة البنش** (Bench Group) هي إصدار Frappe مع قائمة تطبيقات. كل نشر يبني صورة Docker واحدة تعمل
كـ *بنش* على خادم. تعمل عدة إصدارات Frappe (**14 و15 و16**) جنبًا إلى جنب على الخادم نفسه، والإصدار
الافتراضي للمجموعات الجديدة هو v16.

1. **مجموعات البنش ← مجموعة بنش جديدة**.
2. أدخل *الاسم* (حروف صغيرة وأرقام وشرطات)، واختر *إصدار Frappe* و*خادم البناء*.
3. حدّد **تطبيقات المتجر** و**تطبيقاتك المخصصة**. التطبيقات التي لا تدعم الإصدار المختار تظهر بعبارة
   "غير متوافق مع إصدار Frappe هذا".
4. **إنشاء مجموعة بنش**، ثم في صفحة المجموعة اضغط **انشر الآن**. البناء الأول يأخذ وقتًا، وسجل البناء
   يظهر مباشرة تحت *عمليات النشر*.
5. في **البنشات على خوادمك** اختر خادمًا واضغط **نشر على خادم**.

لإضافة تطبيق لاحقًا: **إضافة تطبيق** في صفحة المجموعة ثم **نشر** من جديد. خيار **التحديث التلقائي** مع
نافذة تحديث ينشر البناءات الجديدة تلقائيًا. وتظهر عبارة **يتوفر تحديث** عند دفع تعديلات جديدة إلى
تطبيقاتك المخصصة.

### تطبيقاتك الخاصة من GitHub

1. **مجموعات البنش ← التطبيقات المخصصة ← ربط GitHub** وثبّت تطبيق GitHub الخاص بالمنصة على حسابك أو مؤسستك.
2. **إضافة تطبيق من GitHub**: اختر الحساب والمستودع والفرع؛ يُكتشف اسم التطبيق وإصدارات Frappe المدعومة.
3. مزوّدون آخرون: **إضافة من مزوّد git آخر (GitLab، Gitea، …)** مع رابط المستودع ورمز وصول للقراءة فقط.

## 5. المواقع

### إنشاء موقع

1. **المواقع ← موقع جديد**.
2. **اختر مكان النشر**: *خوادمك* (بنش خاص بك) أو *استضافة مشتركة*.
3. أدخل *اسم الموقع*. في الاستضافة المشتركة يصبح `<name>.<نطاق المنصة>`؛ وعلى خادمك الخاص يمكنك إدخال
   نطاق كامل مثل `erp.example.com`.
4. حدّد *التطبيقات* واختر *الخطة* (على خادمك: "بدون خطة (مشمول في خادمك)").
5. **إنشاء الموقع**. **انسخ كلمة مرور المسؤول الآن**، فلن تظهر مرة أخرى.

في صفحة الموقع الأزرار **فتح الموقع** و**فتح لوحة الإدارة** و**الرؤى** و**تحديث آمن** و**احصل على
مساعدة**، والتبويبات **التطبيقات، النطاقات، النسخ الاحتياطية، الاستخدام، الإعدادات (Config)، البريد
الإلكتروني، دورة الحياة، التخزين، المهام، الإعدادات (Settings)**.

### تثبيت التطبيقات

**التطبيقات ← التطبيقات المتاحة ← تثبيت**. لا تظهر إلا التطبيقات الموجودة في صورة البنش والتي تدعم إصدار
Frappe الخاص بالموقع. إذا احتاج التطبيق تطبيقات أخرى فإنها تُثبّت أولًا (ويُذكر لك أيها). لتحصل على
تطبيقات أكثر، أضفها إلى مجموعة البنش وانشرها. **إلغاء التثبيت** يزيل التطبيق وبياناته من الموقع.

صفحة **متجر التطبيقات** تعرض التطبيقات مع تصفية حسب *إصدار Frappe* و*الفئة*، والإصدارات المدعومة،
والمتطلبات، والسعر، والتقييمات والمراجعات. الفرق التي ثبّتت تطبيقًا تستطيع **قيّم هذا التطبيق** ثم
**حفظ المراجعة**.

### النطاقات المخصصة

1. أنشئ سجل DNS لدى مزوّد DNS **أولًا**: سجل **CNAME** إلى عنوان الموقع للنطاق الفرعي
   (`erp.example.com`)، أو سجل **A/AAAA** إلى IP الخادم للنطاق الرئيسي (`example.com`). تبويب
   **النطاقات** يعرض السجلات المطلوبة بالضبط (*الموصى به* أولًا، مع زر **نسخ**).
2. **النطاقات ← إضافة نطاق**.
3. تتحقق Nexaploy من DNS. الحالة: *بانتظار DNS* ← *جارٍ التحقق* ← *نشط* (أو *معطّل*). يستمر الفحص
   تلقائيًا 72 ساعة، واضغط **تحقق الآن** للفحص فورًا.
4. عندما يصبح النطاق نشطًا تصدر له شهادة Let's Encrypt مجانية. **فحص الشهادات** يعرض حالة TLS (*صالحة*،
   *قاربت على الانتهاء*، *الشهادة الافتراضية*، …).

!!! warning "Cloudflare"
    عند تشغيل البروكسي (السحابة البرتقالية) لا يظهر IP الخادم في السجل. الصفحة تشرح ذلك؛ أوقف البروكسي
    (DNS only) أو اطلب من المشغّل تخطي فحص DNS.

### إعدادات الموقع

**الإعدادات (Config) ← إعادة التحميل** يقرأ `site_config.json` من الخادم. عدّل القيم (JSON: الأرقام
و`true/false` والقوائم والكائنات تُفهم بنوعها)، و**إضافة مفتاح**، ثم **حفظ التغييرات**. الأسرار مخفية،
ومفاتيح قاعدة البيانات والتشفير والمفاتيح التي تديرها Nexaploy للقراءة فقط.

### الاستخدام والخطة

**الاستخدام** يعرض وقت المعالج اليوم والطلبات وحجم قاعدة البيانات والملفات مقارنة بالخطة، وتاريخ 30
يومًا. تجاوز حدود الخطة قد يؤدي إلى تحديد معدل الطلبات أو وضع الصيانة حسب الخطة. يستطيع المالك والمسؤول
وعضو الفوترة **ترقية الخطة** / **تبديل**.

### الإعدادات (Settings)

**ترحيل قاعدة البيانات** يشغّل `bench migrate`. **حذف الموقع** يأخذ نسخة احتياطية ثم يحذف الموقع (اكتب
اسم الموقع للتأكيد).

## 6. النسخ الاحتياطي والاستعادة

### نسخ موقع واحد

**الموقع ← النسخ الاحتياطية**: حدّد **تضمين الملفات** واضغط **نسخ احتياطي الآن**. تعرض القائمة كل نسخة
بنوعها وملفاتها وحجمها وحالتها؛ **تنزيل** يعطي رابطًا صالحًا 15 دقيقة (لتخزين S3 فقط)؛ و**استعادة**
تعيد تلك النسخة إلى الموقع.

النسخ المجدولة تعمل تلقائيًا (يوميًا افتراضيًا؛ تكرارها تضبطه المنصة).

### وجهات النسخ الاحتياطي

افتراضيًا تذهب النسخ إلى تخزين المنصة. يستطيع المالك والمسؤول اختيار وجهتهم الخاصة من صفحة **النسخ
الاحتياطية**:

1. **إضافة وجهة** ← *النوع*: **Google Drive** أو **OneDrive** أو **Dropbox** أو **S3**.
2. أدخل *الاسم* (مثل "Drive الشركة") و*المجلد*. يكتب كل خادم في مجلد فرعي باسم معرّف الخادم.
3. Google Drive / OneDrive / Dropbox: **حفظ وربط**، ثم سجّل الدخول لدى المزوّد ووافق على الوصول. (في Drive
   لا ترى Nexaploy إلا الملفات التي تنشئها.)
   S3: أدخل الحاوية (Bucket) ومزوّد S3 ونقطة الوصول والمنطقة ومعرّف مفتاح الوصول والمفتاح السري، ثم **حفظ**.
4. **اختبار** يفحص الاتصال (ويعرض المساحة المتاحة).
5. حدّد **استخدمها لكل خوادم الفريق التي ليس لها وجهة خاصة**، أو اختر وجهة لكل خادم في جدول *الخوادم*
   (*تُحفظ النسخ في*).

**إعادة الربط** تجدد تصريحًا منتهيًا، و**فصل** يحذف بيانات الدخول.

### مدة الاحتفاظ

في صفحة **النسخ الاحتياطية** يضبط قسم **مدة الاحتفاظ** الإعداد الافتراضي للفريق:

| الإعداد | المعنى |
|---|---|
| الاحتفاظ بالنسخ في التخزين (أيام) | النسخ البعيدة؛ 0 = للأبد |
| الاحتفاظ على الخادم (أيام) | النسخ المحلية؛ 0 = حذفها فور رفعها |
| عدد النسخ اليومية / الأسبوعية / الشهرية المحتفظ بها | نسخ إضافية تُحفظ بعد انتهاء الأيام |

ثم **حفظ الإعداد الافتراضي للفريق**. ولكل موقع يمكنك التحويل من *افتراضي الفريق* إلى *مخصص*. المنصة تحدد
حدًا أدنى وأقصى، وقد يكون الاحتفاظ الأطول إضافة مدفوعة.

### الاستعادة (الكل أو قاعدة البيانات أو الملفات، أو إلى موقع جديد)

1. **النسخ الاحتياطية ← استعادة…** بجانب الموقع.
2. اختر النسخة و**ما الذي تريد استعادته**: *قاعدة البيانات والملفات* أو *قاعدة البيانات فقط* أو
   *الملفات فقط*.
3. **استعادة إلى هذا الموقع** (يستبدل البيانات الحالية)، أو **استعادة كموقع جديد** مع *اسم الموقع الجديد*
   و*البنش* لفحص النسخة بأمان.

### الاستعادة إلى نقطة زمنية

"أعد موقعي إلى ما كان عليه الساعة 3:15 عصر اليوم."

1. **الموقع ← النسخ الاحتياطية ← الاستعادة إلى نقطة زمنية**. تظهر النافذة المتاحة (*متاح من … إلى …*،
   آخر 7 أيام، حتى دقائق قليلة مضت).
2. اختر الوقت (بالمنطقة الزمنية لمتصفحك).
3. اختر **الاستعادة إلى موقع جديد لفحصه أولًا (موصى به)**: البريد مكتوم والمجدول متوقف في النسخة، وتُحسب
   كأي موقع حتى تحذفها. أو **الكتابة فوق هذا الموقع**: كل ما بعد ذلك الوقت يضيع، وتؤخذ نسخة أمان أولًا،
   واكتب اسم الموقع للتأكيد.

## 7. الموقع التجريبي والتحديث الآمن وترقية الإصدار

### الموقع التجريبي (Staging)

**دورة الحياة ← إنشاء موقع تجريبي** ينشئ نسخة (`staging-<site>`) على البنش نفسه: البريد مكتوم، والمجدول
متوقف، وحسابات البريد معطّلة، ولا تُحسب في الفاتورة. **تحديث من الإنتاج** يستبدل بياناتها. احذفها بزر
**حذف الموقع** العادي.

### التحديث الآمن

1. **تحديث آمن** في صفحة الموقع.
2. اختر *المنصة الهدف* أي البنش (الافتراضي: *أحدث بناء لمجموعة المنصات هذه*) واضغط **اختبار التحديث**. تُنشأ نسخة
   على بنش يعمل بالإصدار الجديد، وتُرحّل وتُفحص (ping وصفحة الدخول وقاعدة البيانات). موقعك لا يتغير.
3. إذا *نجح* الاختبار اضغط **تطبيق التحديث** (تؤخذ نسخة احتياطية جديدة أولًا). حدّد *احذف موقع الاختبار
   بعد ذلك*، أو **حذف موقع الاختبار** لاحقًا.
4. إذا *فشل* فاقرأ السجل (**عرض السجل**)، وموقعك يبقى كما هو.

يستطيع مالك مجموعة البنش تفعيل **لا تحدّث تلقائيًا إلا بعد نجاح اختبار التحديث لكل موقع**.

### النقل أو الترقية من v15 إلى v16

1. أنشئ مجموعة بنش v16 بالتطبيقات نفسها (يجب أن يدعم كل تطبيق v16)، وانشرها، ثم انشرها على خادم.
2. **دورة الحياة ← نقل الموقع**: اختر البنش الهدف. للإصدار الأعلى حدّد **ترقية من v15 إلى v16 (يشغّل
   الترحيل؛ لا يمكن التراجع)**. اضغط **نقل**.
3. تؤخذ نسخة من الموقع، وتُستعاد على البنش الهدف، وتُرحّل، ثم يُزال من البنش القديم. النطاقات المخصصة
   تبقى. النقل إلى خادم آخر يتطلب تخزين نسخ المنصة، ويجب بعده توجيه كل نطاقات الموقع إلى الخادم الجديد.
   النقل إلى إصدار أقدم مرفوض.

!!! tip
    جرّب أولًا: نفّذ **تحديثًا آمنًا** إلى بنش v16، أو استعد نسخة كموقع جديد هناك.

### إعادة التسمية

**دورة الحياة ← إعادة تسمية الموقع** ← *الاسم الجديد* ← **إعادة تسمية**. قاعدة البيانات والملفات تبقى
كما هي، والاسم القديم يُحفظ كنطاق فتظل الروابط القديمة تعمل. يدخل الموقع وضع الصيانة لحظات.

### النقل إلى فريق آخر

1. **دورة الحياة ← النقل إلى فريق آخر**: أدخل الفريق أو بريدًا إلكترونيًا، ثم **طلب النقل**.
2. يفتح مالك أو مسؤول الفريق المستلم الرابط ويضغط **قبول النقل** (أو **رفض**). من وقتها يملكون الموقع
   ويدفعون ثمنه، وتنتقل نسخه معه.

لا يغيّر الفريقَ إلا موقع على الاستضافة المشتركة؛ انقل الموقع من خادمك الخاص أولًا.

## 8. الرؤى ووحدة التحكم والتدقيق

**الرؤى** في صفحة الموقع فيها هذه التبويبات:

| التبويب | المحتوى | من (افتراضيًا) |
|---|---|---|
| التحليلات | الطلبات، الوسيط والنسبة 95 لزمن الاستجابة، المهام الخلفية، أكثر المسارات، رموز الحالة | الجميع |
| السجلات | الويب، العمّال الخلفيون، المجدول، سجل Frappe، سجل الأخطاء | المالك، المسؤول، المطوّر |
| الاستعلامات البطيئة | استعلامات قاعدة البيانات البطيئة مجمّعة | المالك، المسؤول، المطوّر |
| SQL | **تشغيل الاستعلام**، **للقراءة فقط** افتراضيًا، **تنزيل CSV** | القراءة: المالك والمسؤول والمطوّر؛ الكتابة: المالك والمسؤول |
| وحدة التحكم | **تنفيذ** كود Python داخل الموقع كمسؤول، مع **اعتماد تغييرات قاعدة البيانات** اختياريًا | المالك، المسؤول |

!!! warning
    SQL في وضع الكتابة وكود وحدة التحكم المعتمد يغيّران البيانات فورًا ولا يمكن التراجع عنهما. خذ نسخة
    احتياطية أولًا. وحدة التحكم مرفوضة على البنشات المشتركة مع فرق أخرى.

**النشاط ← صلاحيات وحدة التحكم** (للمالك والمسؤول): غيّر صلاحيات كل عضو (*مخصص* أو *افتراضيات الدور*)،
و**اشتراط المصادقة الثنائية لـ SQL ووحدة التحكم**، واقرأ **سجل تدقيق وحدة التحكم**: كل استعلام وتشغيل
لوحدة التحكم وعرض للسجلات، بما في ذلك المحاولات المرفوضة. لا يمكن تعديله أو حذفه.

## 9. إضافات البريد والتخزين

### البريد المُدار

1. **الموقع ← البريد الإلكتروني ← تفعيل البريد المُدار**. يحصل الموقع على حساب بريد صادر اسمه
   "Nexaploy Relay"، ويُرسل البريد عبر مرحّل المنصة (بحد يومي).
2. اختياريًا **نطاق إرسال مخصص**: أدخل نطاقك ثم **حفظ**، وأنشئ سجلات SPF وDKIM وDMARC الظاهرة، ثم
   **تحقق من DNS**. بعد أن يصبح *تم التحقق* يُرسل البريد باسم `noreply@<نطاقك>`، وقبلها يُستخدم المرسل
   الافتراضي.

### المرفقات خارج الخادم ونسخة التعافي وسلة المحذوفات

إضافات مدفوعة (إذا وفّرتها المنصة)، في **الموقع ← التخزين**:

1. **تخزين المرفقات**: *على قرص الخادم* أو *على التخزين السحابي*.
2. اختر *الحاوية الأساسية*، واختياريًا **نسخة متماثلة (التعافي من الكوارث)** في منطقة أخرى، و**سلة
   المحذوفات للملفات المحذوفة** مع *الاحتفاظ بالملفات المحذوفة لمدة (أيام)*.
3. احفظ. تُنقل الملفات والموقع يعمل.
4. **فحص الحالة** يعرض من أين تُقدَّم الملفات وآخر تكرار وسلامة التحميل.
5. إذا تعطلت المنطقة الأساسية: **التحويل إلى النسخة المتماثلة**، ثم لاحقًا **العودة إلى الأساسية**.
6. **عرض الملفات المحذوفة** يعرض السلة، ويمكنك استعادة ملف منها.

نسخ الموقع الذي نُقلت ملفاته تحتوي قاعدة البيانات فقط (الملفات أصلًا خارج الخادم).

## 10. مراقبة التوفر وصفحة الحالة

كل موقع نشط يحصل على مراقب افتراضي تلقائيًا. في **المراقبة**:

- **إضافة مراقب**: الاسم، الموقع، *العنوان* (الموقع أو نطاق مخصص نشط)، المسار، الطريقة، *الحالة
  المتوقعة* (`200` أو `200-299` أو `2xx`)، *الكلمة المفتاحية (اختياري)*، الفاصل الزمني، المهلة،
  *عدد الإخفاقات قبل التنبيه*، *النصاب*، *المسابير*. ثم **حفظ المراقب**. الفحص كل دقيقة وأكثر من 3
  مراقبين للموقع يحتاجان ميزة المراقبة المتقدمة.
- **إيقاف مؤقت** / **استئناف** / **تعديل** / **حذف** المراقب (الافتراضي يمكن إيقافه مؤقتًا فقط).
- **الحوادث**: حدد *العنوان العام*، و**إخفاء من صفحة الحالة**، و**نشر تحديث**.
- **صفحة الحالة**: العنوان، الوصف، *نطاق مخصص (اختياري)*، منشورة، *عرض سجل الحوادث*، و*المراقبون في
  الصفحة* مع *الاسم العام*. اضغط **حفظ صفحة الحالة** ثم **فتح صفحة الحالة** (`/status/<slug>`). الزوار لا
  يرون إلا الأسماء العامة، ولا يرون الروابط أو الأخطاء أبدًا. للنطاق المخصص أنشئ CNAME إلى لوحة التحكم
  واطلب من المشغّل توجيهه.

## 11. الإشعارات

افتراضيًا تُرسل التنبيهات وإشعارات الفوترة بالبريد إلى فريقك. **الإشعارات ← إضافة قناة** (للمالك والمسؤول)
يرسلها إلى أماكن أخرى. بعد إضافة قناة تذهب الإشعارات إلى قنواتك فقط (تُضاف قناة *البريد الإلكتروني*
تلقائيًا حتى يستمر البريد؛ عطّلها إن لم تحتجها).

الأحداث: الخادم غير متصل، عودة الخادم، القرص ممتلئ تقريبًا، حاويات غير سليمة، الموقع متوقف، عودة الموقع،
فشل النسخ الاحتياطي، فشل مهمة، صدور فاتورة، فشل الدفع، إيقاف المواقع، رد الدعم، المراقب متوقف، عودة
المراقب، وصحة الخادم حرجة / عادت سليمة.

### تيليجرام خطوة بخطوة

1. في تيليجرام افتح **@BotFather** وأرسل `/newbot`، واختر اسمًا واسم مستخدم ينتهي بـ `bot`. يرد عليك
   BotFather بـ **رمز البوت** (`123456:ABC…`).
2. افتح البوت الجديد وأرسل له أي رسالة (مثل `/start`). لمجموعة: أضف البوت إلى المجموعة وأرسل فيها
   `/start@<اسم مستخدم البوت>`.
3. في لوحة التحكم: **الإشعارات ← إضافة قناة**، *النوع* **تيليجرام**، واكتب *الاسم*، والصق **رمز البوت**.
4. اضغط **اكتشاف المحادثة** واختر محادثتك (أو المجموعة)، فيُملأ *معرّف المحادثة*. إذا لم يُعثر على شيء
   فأرسل رسالة إلى البوت وأعد المحاولة.
5. حدّد **الأحداث**، وأبقِ *مفعّلة*، ثم **حفظ القناة**.
6. **إرسال تجريبي**. تصبح الحالة *تعمل*.

### واتساب (Meta Cloud API)

*معرّف رقم الهاتف* و*رمز الوصول* من تطبيق WhatsApp Business لدى Meta، و*رقم المستلم* (بالصيغة الدولية)،
واختياريًا *اسم القالب* و*لغة القالب* (مثل `en_US` أو `ar`). بدون قالب معتمد لا يوصل واتساب الرسائل إلا خلال
24 ساعة من آخر رسالة أرسلها المستلم إلى رقمك؛ ومع قالب (بمتغير واحد `{{1}}`) تُوصَل دائمًا.

### Slack وDiscord

أنشئ incoming webhook (في Slack: `https://hooks.slack.com/services/…`؛ وفي Discord: إعدادات القناة ←
Integrations ← Webhooks، ‏`https://discord.com/api/webhooks/…`) والصقه في *رابط Webhook*.

### Webhook عام والتحقق من التوقيع

*رابط Webhook* (https وعنوان عام) و*سر التوقيع (اختياري)*. يُرسل كل حدث كـ JSON بطريقة POST:
`{event, title, message, context, url, team, timestamp}`. مع السر تحمل الترويسة
`X-Nexaploy-Signature: sha256=<hex>` قيمة HMAC-SHA256 لـ **جسم الطلب الخام**. تحقق منها قبل الوثوق بالطلب:

=== "Python"

    ```python
    import hashlib, hmac

    def verify(raw_body: bytes, header: str, secret: str) -> bool:
        expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
        return hmac.compare_digest(expected, header or "")
    ```

=== "Node.js"

    ```javascript
    const crypto = require("crypto");

    function verify(rawBody, header, secret) {
      const expected = "sha256=" + crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
      const a = Buffer.from(expected), b = Buffer.from(header || "");
      return a.length === b.length && crypto.timingSafeEqual(a, b);
    }
    ```

استخدم بايتات الطلب الخام، لا JSON بعد إعادة تحويله.

## 12. الفوترة

**الفوترة** (للمالك والمسؤول وعضو الفوترة):

- **رصيد الحساب**: الرصيد المسبق يدفع الفواتير الجديدة تلقائيًا قبل خصم أي بطاقة. **إضافة رصيد** ←
  *المبلغ* و*الدفع عبر* (Stripe أو Paymob) ← **شحن**.
- **سجل الرصيد**: كل شحن ودفع وتسوية.
- **الفواتير**: فاتورة كل شهر عن الشهر السابق (المواقع والخوادم والتطبيقات المدفوعة والإضافات) مع *الرصيد
  المستخدم* و*المبلغ المستحق*. **ادفع** يفتح صفحة الدفع.

!!! warning "الإيقاف"
    الفاتورة غير المدفوعة تصبح *متأخرة* بعد تاريخ استحقاقها. وبعد عدد الأيام الذي تحدده المنصة تُوقف مواقع
    الفريق (**موقوف** = وضع الصيانة). دفع الفاتورة يرفع الإيقاف تلقائيًا.

## 13. الدعم

1. **الدعم ← تذكرة جديدة** (أو **احصل على مساعدة** في صفحة الموقع).
2. *الموضوع*، و*الأولوية* (يظهر زمن أول رد المتوقع)، و*الموقع* أو *الخادم*، و*صف المشكلة*. ثم **فتح تذكرة**.
3. تصلك الردود بالبريد؛ ردّ بـ **إرسال الرد**. **إغلاق التذكرة** عند الانتهاء، و**إعادة فتح** عند الحاجة.
   التذاكر المحلولة تُغلق بعد 7 أيام.

لا تشارك كلمات المرور أو أسرار API في أي تذكرة.

## 14. نشر تطبيقاتك

1. **الناشر ← كن ناشرًا**: اسم الناشر، الموقع، بريد الدعم، *طريقة الدفع* (تحويل بنكي أو PayPal أو رصيد)
   وبيانات الدفع.
2. **إدراج جديد**: اختر أحد تطبيقاتك المخصصة. يجب أن يكون المستودع **عامًا**.
3. املأ العنوان والفئة والتسعير (مجاني / مدفوع مع *السعر لكل موقع شهريًا*) والوصف ورابط الشعار ورابط
   التوثيق والتطبيقات المطلوبة وصور الشاشة.
4. **إرسال للمراجعة**. يوافق فريق المنصة أو يرفض مع ملاحظات؛ و**سحب** يعيده للتعديل أثناء المراجعة. عند
   الموافقة يُنشأ إصدار لكل إصدار Frappe، وكل إصدار يُبنى تجريبيًا قبل أن يستطيع العملاء تثبيته.
5. **الإيرادات حسب الشهر** و**الدفعات** تعرض حصتك (80 % افتراضيًا)، وتُدفع شهريًا.

## 15. أسئلة شائعة

**ماذا يحدث لمواقعي إذا تركت المنصة؟** تستمر في العمل. إزالة الوكيل تُبقي البنشات والمواقع وقاعدة
البيانات والوكيل العكسي تعمل كمشاريع Docker Compose عادية في `/opt/nexaploy`.

**ما الإصدارات المدعومة؟** Frappe/ERPNext 14 و15 و16، جنبًا إلى جنب.

**هل تحتاج المنصة SSH إلى خادمي؟** لا. فقط المنفذان 80/443 لمواقعك.

**لماذا ما زال نطاقي "بانتظار DNS"؟** السجل لا يشير إلى الخادم بعد، أو يخفيه بروكسي Cloudflare. تغييرات
DNS قد تأخذ وقتًا؛ اضغط **تحقق الآن**.

**يظهر تحذير شهادة على موقعي.** يجب أن يشير النطاق إلى الخادم وأن يكون المنفذ 80 مفتوحًا. راجع **النطاقات
← فحص الشهادات**.

**هل أستطيع استعادة سجل واحد محذوف؟** استعد نسخة أو نقطة زمنية **إلى موقع جديد**، ثم انقل البيانات منه.

**هل أستطيع تنزيل نسخي؟** نعم، من **الموقع ← النسخ الاحتياطية ← تنزيل** عندما يكون التخزين S3؛ ونسخ
Drive/OneDrive/Dropbox موجودة أصلًا في تخزينك السحابي.

**لماذا موقعي في وضع الصيانة؟** تجاوز حدود خطته (راجع **الاستخدام**)، أو هناك فاتورة متأخرة، أو تجري
استعادة أو إعادة تسمية.

**هل يكسر تحديث النظام مواقعي؟** لا. التحديثات تعمل على المضيف، والمواقع تعود تلقائيًا بعد إعادة التشغيل.
