# دليل المشغّل

هذا الدليل موجّه إلى **المشغّل**: الشخص أو الشركة التي تدير منصة Nexaploy (اللوحة الأم)
وتدخل بحساب `Administrator` أو بأي مستخدم له دور **System Manager**. أما العملاء فيقرؤون
[دليل العميل](customer.md).

بصفتك مشغّلًا فأنت من يثبّت لوحة التحكم، ويربط الخوادم، ويحدد الأسعار والتخزين والبريد والعلامة
التجارية، ويراجع تطبيقات المتجر، ويطلق إصدارات الوكيل، ويحافظ على سلامة كل شيء.

!!! note "مكانان للعمل"
    - **لوحة العميل** على `https://<control-plane>/dashboard`. يظهر لمسؤولي المنصة بند إضافي في
      القائمة الجانبية هو **الإدارة** (Administration) على `/dashboard/admin`، وبند
      **لوحة الإدارة** (Admin desk).
    - **مكتب Frappe** (Desk) على `https://<control-plane>/app`. بعض الأشياء موجودة في المكتب فقط:
      *Nexaploy Settings* (النطاق الجذري) و*Cloud Provider* و*GitHub Settings* و*Uptime Probe*
      و*SaaS Product* والرد على *Support Ticket* و*Publisher Payout* وإعادة تشغيل *Agent Job*.

!!! tip "عن أسماء الأزرار"
    نكتب اسم الزر كما يظهر في الواجهة العربية، ويليه أحيانًا الاسم الإنجليزي بين قوسين حتى تجده
    مهما كانت لغة الواجهة.

## 1. اختر نموذج التثبيت

| النموذج | ما الذي يعمل وأين | مناسب لـ |
|---|---|---|
| **الكل في خادم واحد** (all-in-one) | لوحة التحكم والمواقع على خادم **واحد** (`install.sh --with-control-plane`) | شركة واحدة، أو وكالة صغيرة، أو تجربة |
| **لوحة تحكم مستضافة + خوادم** | لوحة التحكم على بنش Frappe مستقل، وخوادم كثيرة (مستضافة على Hetzner/DigitalOcean أو خوادم العملاء BYOS) تنضم إليها برمز | شركة استضافة لديها عملاء كثيرون |

النموذجان يستخدمان الكود نفسه. عيب نموذج الخادم الواحد: إذا توقف الخادم توقفت معه لوحة التحكم
وتنبيهاتها، لذلك اجعل تخزين النسخ الاحتياطية **خارج الخادم** في هذه الحالة.

### متطلبات كل خادم

| البند | المطلوب |
|---|---|
| نظام التشغيل | Ubuntu 22.04 أو 24.04 (وDebian 12 بأفضل جهد)، بمعمارية x86_64 أو aarch64 |
| الذاكرة | 2 جيجابايت على الأقل (يفضل 4 أو أكثر؛ كل بنش يستهلك نحو 1–2 جيجابايت) |
| القرص | 20 جيجابايت فارغة على الأقل تحت `/opt/nexaploy` |
| المنافذ الواردة | **80 و443** فقط، مفتوحة للإنترنت (Let's Encrypt يتحقق عبر المنفذ 80) |
| الاتصال الصادر | HTTPS إلى Docker Hub/GHCR وGitHub وrclone.org ولوحة التحكم |
| الصلاحيات | root (sudo). المنصة لا تحتاج SSH إلى الخادم أبدًا. |

## 2. التثبيت على خادم واحد (all-in-one)

1. أنشئ سجل DNS من النوع **A** (وAAAA إن كان للخادم IPv6) لنطاق لوحة التحكم، مثل
   `cloud.example.com`، يشير إلى الخادم.
2. شغّل المثبّت بصلاحيات root:

    ```bash
    curl -fsSL https://raw.githubusercontent.com/a7733mai/NexaPloy-/main/agent/install/install.sh \
      | sudo bash -s -- --with-control-plane cloud.example.com --acme-email ops@example.com
    ```

    إذا شغّلته بلا خيارات ومن طرفية، يسألك المثبّت بدلًا من ذلك:

    ```
    Nexaploy setup
      1) New: install the control plane on this server (all-in-one)
      2) Join: connect this server to an existing control plane
      3) Standalone agent only (CLI, no control plane)
    ```

    الخيار 1 يسأل عن النطاق وعن بريد Let's Encrypt.

    قبل البدء يتحقق المثبّت من أن نطاق لوحة التحكم يشير إلى هذا الخادم (فحص DNS مسبق)، لأن
    الشهادة لا تصدر بدون ذلك. يمكنك تخطي الفحص بـ `--skip-dns-check` (مثلًا خلف موازن أحمال).
    صورة لوحة التحكم تُختار تلقائيًا، وإذا تعذّر سحبها يبنيها المثبّت محليًا.
3. في النهاية يطبع المثبّت:

    ```
    ==> Control plane: https://cloud.example.com
      login:    Administrator
      password: stored in /opt/nexaploy/config/control-plane.env (ADMIN_PASSWORD)
    ```

4. اقرأ كلمة المرور وادخل:

    ```bash
    sudo grep ADMIN_PASSWORD /opt/nexaploy/config/control-plane.env
    ```

    يمكنك اختيارها بنفسك بالخيار `--admin-password`. صلاحيات الملف 600؛ غيّر كلمة المرور بعد
    أول دخول (**الحساب ← تغيير كلمة المرور**) واحفظ الملف بأمان.

ما الذي يفعله التثبيت الشامل: ينشئ بنشًا اسمه `nexaploy-cp` من الصورة
`ghcr.io/a7733mai/nexaploy-control-plane:16` (يمكن تغييرها بـ `--control-plane-image`)، ويفتحه على
`127.0.0.1:8090` فقط ليصل إليه الوكيل المحلي (`--control-plane-port`)، وينشئ موقعًا لنطاقك فيه
تطبيق `nexaploy`، وينشئ فريق المشغّل **Platform** (معفى من الفوترة)، ثم يسجّل الخادم في لوحة
التحكم الخاصة به. يُعلَّم الخادم بأنه مضيف لوحة التحكم: لا يمكن أرشفته، ولا تستطيع لوحة التحكم
حذف نفسها أو نقلها. مهمة يومية تأخذ نسخة احتياطية من موقع لوحة التحكم (تُرفع بعد ضبط تخزين النسخ).

!!! tip "صور الخوادم الجاهزة"
    صور Hetzner Cloud / DigitalOcean المبنية من `packer/` تُكمل التثبيت عند أول إقلاع. ضع في
    user-data القيمة `NEXAPLOY_DOMAIN=cloud.example.com` (للتثبيت الشامل) أو
    `NEXAPLOY_CONTROL_PLANE=…` مع `NEXAPLOY_TOKEN=…` (للانضمام).

## 3. تثبيت لوحة تحكم مستضافة مع خوادم منفصلة

1. ثبّت تطبيق Frappe على بنش Frappe v15 أو v16:

    ```bash
    git clone https://github.com/a7733mai/NexaPloy- /srv/nexaploy
    cd ~/frappe-bench
    bench get-app /srv/nexaploy/control-plane
    bench --site cp.example.com install-app nexaploy
    bench --site cp.example.com migrate
    bench --site cp.example.com enable-scheduler
    ```

    كلمة مرور `Administrator` هي التي أعطيتها لأمر `bench new-site`.
2. انشر المثبّت على `https://<control-plane>/install.sh` (مثال nginx):

    ```nginx
    location = /install.sh { alias /srv/nexaploy/agent/install/install.sh; default_type text/x-shellscript; }
    ```

3. في المكتب افتح **Nexaploy Settings** واضبط **النطاق الجذري** (root domain): المواقع المشتركة
   الجديدة تأخذ الاسم `<name>.<root domain>`. وجّه سجلًا عامًا `*.<root domain>` إلى خوادمك المستضافة.
4. أضف الخوادم (القسم التالي).

## 4. إضافة الخوادم

=== "خادم خاص BYOS (للعميل أو للمشغّل)"

    1. في لوحة التحكم افتح **الخوادم ← أضف خادمك الخاص ← إنشاء أمر التثبيت**
       (Servers → Add your own server → Generate install command).
    2. شغّل الأمر الظاهر بصلاحيات root على خادم Ubuntu جديد:

        ```bash
        curl -fsSL https://cp.example.com/install.sh | sudo bash -s -- \
          --token <registration-token> --control-plane https://cp.example.com
        ```

    3. تعرض الصفحة "بانتظار تسجيل خادمك…" ثم "خادمك متصل ونشط". الرمز يُستخدم مرة واحدة
       وصالح 24 ساعة.

=== "خادم مستضاف (تنشئه المنصة)"

    1. في المكتب أنشئ **Cloud Provider** (Hetzner أو DigitalOcean مع رمز API) ثم شغّل
       **Sync catalog**. تُستورد المناطق والأحجام **معطّلة**.
    2. فعّل المناطق التي تبيعها، ولكل **Cloud Server Size** فعّله واربطه بخطة **Nexaploy Plan** من
       نوع *Server Hosted* (السعر الذي يدفعه العميل). الأحجام بلا خطة لا تُعرض.
    3. يستخدم العملاء (أو أنت ضمن فريق Platform) **الخوادم ← إنشاء خادم مستضاف**، ويختارون المزوّد
       والمنطقة وحجم الخادم ثم **Create server**. يقلع الخادم ويشغّل `install.sh` عبر cloud-init ويسجّل
       نفسه خلال 5–10 دقائق. إذا لم يسجّل خلال 20 دقيقة يُعلَّم *Failed* وتصلك رسالة تنبيه.

=== "خادم مستضاف يدويًا"

    أنشئ **Server** في المكتب (ownership = *Hosted*)، واستدعِ **Rotate token**، ثم ثبّت بالخيارات
    `--server-id <id> --token <server token> --control-plane https://cp.example.com`.

### كل خيارات `install.sh`

| الخيار | المعنى |
|---|---|
| `--control-plane URL` | الانضمام إلى لوحة التحكم هذه (مع `--token`). |
| `--token TOKEN` | مع `--control-plane`: رمز التسجيل لمرة واحدة. وحده: رمز الواجهة البرمجية المحلية. |
| `--with-control-plane DOMAIN` | تثبيت شامل: تثبيت لوحة التحكم على هذا الخادم. |
| `--control-plane-image IMG` | صورة لوحة التحكم (الافتراضية `ghcr.io/a7733mai/nexaploy-control-plane:16`). |
| `--control-plane-port PORT` | المنفذ المحلي الذي يصل منه الوكيل إليها (الافتراضي `8090`). |
| `--admin-password PASS` | كلمة مرور Administrator (عشوائية افتراضيًا، تُحفظ في `config/control-plane.env`). |
| `--skip-dns-check` | تثبيت شامل: عدم التحقق من أن نطاق لوحة التحكم يشير إلى هذا الخادم. |
| `--restore-control-plane BACKUP` | تثبيت شامل: استعادة نسخة احتياطية موجودة للوحة التحكم على هذا الخادم الجديد (نقل لوحة التحكم). |
| `--server-id ID` | معرّف ثابت للخادم. |
| `--acme-email EMAIL` | بريد حساب Let's Encrypt. اضبطه دائمًا. |
| `--agent-source SRC`, `--branch BRANCH` | مصدر كود الوكيل (استخدم وسم إصدار في الإنتاج). |
| `--frappe-docker-ref REF` | مرجع `frappe_docker` لبناء الصور. |
| `--force-register` | إعادة التسجيل رغم وجود رمز محفوظ. |
| `--skip-preflight` | تخطي فحوص النظام والمعمارية والذاكرة والقرص والمنافذ. |
| `--skip-packages` | عدم تثبيت حزم النظام (ويتخطى ترقية النظام أيضًا). |
| `--no-os-upgrade` | عدم ترقية نظام التشغيل قبل التثبيت. |
| `--hwe-kernel` | لـ Ubuntu فقط: تثبيت نواة HWE الأحدث (`linux-generic-hwe-<version>`) أيضًا. |
| `--no-reboot` | عدم إعادة التشغيل أبدًا حتى لو احتاجت الترقية ذلك. |
| `--no-systemd` | عدم تثبيت وحدات systemd. |
| `--skip-frappe-docker` | عدم نسخ `frappe_docker` (لن يبني هذا الخادم صورًا). |
| `--root DIR` | مجلد التثبيت (للاختبار فقط). |
| `-y`, `--yes` | عدم طرح أي أسئلة. |

راجع أيضًا [مرجع التثبيت](../install.md). إعادة تشغيل المثبّت آمنة: يرقّي الوكيل ويحتفظ بـ
`agent.toml` و`db.env` والشهادات والأسرار.

### ترقية نظام التشغيل أثناء التثبيت

قبل أن يثبّت أي شيء (بعد الفحوص المسبقة مباشرة) يحدّث `install.sh` الخادم بالكامل:

1. `apt-get update` ثم `apt-get full-upgrade` (بدون أسئلة، مع الإبقاء على ملفات الإعداد الحالية).
   هذا يثبّت أيضًا أحدث نواة (kernel) في إصدار التوزيعة.
2. `apt-get autoremove`.
3. مع `--hwe-kernel` (Ubuntu فقط) يثبّت أيضًا نواة HWE ‏`linux-generic-hwe-<version>`.

إذا احتاجت الترقية إعادة تشغيل (النواة الجديدة تنشئ `/var/run/reboot-required`)، **يكمل المثبّت
التثبيت أولًا** ثم يعيد تشغيل الخادم تلقائيًا **بعد دقيقة واحدة**. في الوضع التفاعلي يسألك أولًا
(الإجابة الافتراضية: نعم). تعود البنشات والمواقع والوكيل العكسي وMariaDB تلقائيًا بعد إعادة التشغيل
(سياسات إعادة التشغيل في Docker ووحدات systemd).

| الخيار | الأثر |
|---|---|
| `--no-os-upgrade` | تخطي ترقية النظام. |
| `--skip-packages` | يتخطى الحزم **و**ترقية النظام. |
| `--hwe-kernel` | Ubuntu: تثبيت نواة HWE أيضًا. |
| `--no-reboot` | عدم إعادة التشغيل؛ أعد التشغيل لاحقًا في الوقت المناسب لك. |

## 5. أول دخول ومنطقة الإدارة

1. افتح `https://<control-plane>/login` وادخل باسم `Administrator`.
2. افتح **الإدارة** (Administration) من القائمة الجانبية (`/dashboard/admin`). لا يفتحها إلا مسؤولو
   المنصة (Administrator ومن لهم دور System Manager)؛ العملاء يحصلون على *403*.

في الصفحة سبعة تبويبات.

### 5.0 قائمة الإعداد الأولي

في المنصة الجديدة تبدأ صفحة الإدارة بقائمة إعداد. نفّذها بهذا الترتيب، وكل بند يأخذك إلى مكان ضبطه:

1. اسم المنصة ونطاقها (العلامة التجارية والنطاق الجذري).
2. العملة (الفوترة).
3. بوابة دفع (Stripe أو Paymob).
4. تخزين النسخ الاحتياطية (ملف تخزين يُستخدم لنسخ المنصة).
5. البريد الصادر (حساب البريد الخاص بلوحة التحكم، واختياريًا مرحّل البريد المُدار).
6. الخطط والأسعار.
7. مسبار خارجي لمراقبة التوفر.
8. موقع تجريبي لترى المسار كاملًا يعمل.

### 5.1 نظرة عامة (Overview)

عرض للقراءة فقط لصحة المنصة كلها:

| البطاقة | تعرض |
|---|---|
| الخوادم | المتصلة / غير المتصلة |
| المواقع | العدد وعدد الفرق |
| المهام الفاشلة (24 ساعة) | مهام الوكيل الفاشلة، مع روابط للمكتب في الجدول أسفلها |
| التذاكر المفتوحة | وعدد التي تأخر أول رد عليها |
| MRR | الإيراد الشهري المتكرر للاشتراكات النشطة (بدون الفرق المعفاة) |
| الفواتير المتأخرة | العدد |
| الوكلاء القدامى | خوادم أقدم من آخر إصدار منشور للوكيل |
| الإدراجات قيد المراجعة | تطبيقات متجر تنتظر مراجعتك |
| المواقع حسب الحالة / حسب إصدار Frappe | التوزيع |
| صحة الخوادم | لوحة صحة الأسطول (الخوادم حسب حالتها)، وإصدارات الوكيل، و**تنبيهات القرص** (خوادم ≥ 85 %) |
| آخر تغييرات المنصة | كل تغيير في هذه المنطقة (من، وماذا، ومتى) |

### 5.2 الميزات والأسعار (Features & pricing)

**الخطط والإضافات.** اضغط **خطة جديدة** أو **تعديل** على أي صف.

| الحقل | المعنى |
|---|---|
| العنوان، النوع | *Site* أو *Server Hosted* أو *Server BYOS* أو *Add-on* |
| السعر الشهري، العملة | ما يدفعه العميل |
| أقصى عدد للمواقع | 0 = بلا حد |
| ثواني المعالج يوميًا، أقصى تخزين (MB)، أقصى قاعدة بيانات (MB) | حدود الموقع، 0 = بلا حد |
| عند تجاوز الحد | *Notify* (بريد)، *Throttle* (تحديد معدل الطلبات أثناء تجاوز ميزانية المعالج)، *Suspend* (وضع الصيانة أثناء تجاوز أي حد) |
| الترتيب | اقتراحات الترقية تصعد بهذا الترتيب |
| مفعّلة | **تعطيل** يخفي الخطة من الاختيارات الجديدة |

الخطط الافتراضية بعد التثبيت: خادم BYOS بـ 10 دولارات شهريًا، Hosted Small بـ 40، Site Basic بـ 5.

**المرفقات خارج الخادم ونسخة التعافي وسلة المحذوفات.** فعّل المرفقات خارج الخادم ونسخة التعافي
وسلة المحذوفات، وقرر هل **يمكن للعملاء استخدام حاوياتهم الخاصة**، واختر الحاويات الافتراضية
(الأساسية والمتماثلة والسلة)، و*فترة التكرار بالدقائق* (15)، و*أقصى عدد حذف في كل مزامنة*، و*طريقة
مقارنة الملفات*، ومدد الاحتفاظ في السلة، و*حجم الذاكرة المؤقتة لكل تحميل*، و**أسعار الإضافات (لكل
موقع شهريًا)**.

**النسخ الاحتياطية والوكلاء.** الحد الأدنى والأقصى ومدة الاحتفاظ المضمّنة (بالأيام)، وأقصى احتفاظ
محلي، وأقصى عدد للنسخ الشهرية، و*الفرق التي لديها إضافة الاحتفاظ الممتد*، و*مهلة ترقية الوكيل
(دقائق)*، و*رابط مستودع الوكيل*، و**يمكن للعملاء ترقية الوكيل على خوادمهم الخاصة**، و*بريد
التنبيهات*، و*السجل* (Registry) واسم المستخدم وكلمة المرور.

!!! tip "سجل الصور (Registry)"
    بدون سجل صور تبقى الصورة على الخادم الذي بناها فقط. اضبط *Registry* (مثل `ghcr.io/your-org`)
    لتُرفع الصور المبنية وتستطيع كل الخوادم سحبها.

**الفوترة.** *الفوترة مفعّلة*، *العملة*، *الضريبة (%)*، *يوم الفوترة*، *أيام السماح*، *الإيقاف بعد
(أيام)*، *خطة خادم BYOS*، *خطة الموقع الافتراضية*، *رصيد التسجيل*، *أدنى وأقصى مبلغ شحن*، *عنوان
العودة بعد الدفع*، وبوابات الدفع:

| البوابة | الحقول | رابط Webhook الذي تسجّله لدى المزوّد |
|---|---|---|
| **Stripe** | مفعّلة، المفتاح القابل للنشر، المفتاح السري، سر الـ webhook | `https://<cp>/api/method/nexaploy.api.billing.stripe_webhook` |
| **Paymob** | مفعّلة، معرّف التكامل، معرّف iframe، العملة، سعر الصرف، عنوان API الأساسي، مفتاح API، سر HMAC | `https://<cp>/api/method/nexaploy.api.billing.paymob_webhook` (للإشعار ولرجوع المتصفح) |

!!! note "الأسرار"
    الأسرار لا تُعرض مرة أخرى أبدًا؛ السر المحفوظ يظهر هكذا `••••last4`. اترك الحقل فارغًا للإبقاء
    عليه، واستخدم زر الإزالة لمسحه.

كيف تعمل الفوترة: في *يوم الفوترة* تحصل كل فرقة على فاتورة واحدة عن الشهر السابق، يُخصم الرصيد
المسبق منها أولًا. تستحق بعد *أيام السماح*، ثم تصبح غير المدفوعة **متأخرة**، وبعد *الإيقاف بعد
(أيام)* تُوقف مواقع الفريق النشطة (**موقوف** = وضع الصيانة). الدفع عبر Stripe/Paymob يعلّم الفاتورة
مدفوعة ويرفع الإيقاف تلقائيًا.

### 5.3 التخزين والنسخ الاحتياطية (Storage & backups)

**ملفات التخزين (حاويات متوافقة مع S3).** **ملف جديد** ← معرّف الملف، العنوان، المزوّد (AWS،
IDrive، Wasabi، B2، R2، MinIO، Hetzner، Other)، تسمية المنطقة، نقطة الوصول (Endpoint)، المنطقة،
طريقة العنونة، الحاوية (Bucket)، بادئة المسار، مفتاح الوصول، المفتاح السري. زر **اختبار** يفحص الملف
من أحد الخوادم (كتابة وحذف وسرد)، و**حذف** يزيله.

**تخزين النسخ الاحتياطية للمنصة.** اختر ملفًا في *استخدام ملف التخزين هذا لنسخ قواعد البيانات
الاحتياطية* ثم **تطبيق**. بعدها ترفع كل الخوادم نسخها إلى تلك الحاوية تحت
`<prefix>/<server_id>/<bench>/<site>/<timestamp>`، ولهذا تُستعاد نسخة خادم على خادم آخر.

**تطبيقات Google Drive وOneDrive وDropbox.** يستطيع العملاء إرسال النسخ إلى تخزينهم السحابي الخاص.
أنشئ تطبيق OAuth لكل مزوّد واملأ معرّف Google وسرّه، ومعرّف Microsoft وسرّه، و*Microsoft tenant*
(الافتراضي `common`)، ومفتاح Dropbox وسرّه. سجّل **عنوان إعادة التوجيه** الظاهر في الصفحة (زر
**نسخ**) لدى كل مزوّد:

```
https://<control-plane>/api/method/nexaploy.api.backup_destinations.oauth_callback
```

| المزوّد | أين | الصلاحية |
|---|---|---|
| Google | Google Cloud Console ← APIs & Services ← Credentials ← OAuth client (Web application) | `drive.file` (لا ترى Nexaploy إلا الملفات التي تنشئها) |
| Microsoft | Entra ID ← App registrations ← Web redirect URI | `offline_access Files.ReadWrite User.Read` |
| Dropbox | App Console ← OAuth 2 ← Redirect URIs | وصول دائم (offline) |

### 5.4 البريد والعلامات التجارية (E-mail & brands)

**مرحّل البريد المُدار.** يتيح لمواقع العملاء الإرسال عبر خادم SMTP موثّق تملكه. املأ المزوّد
(Generic SMTP أو Amazon SES أو Postmark أو Mailgun أو Brevo)، ومضيف SMTP ومنفذه، والتشفير، واسم
المستخدم وكلمة المرور، و*نطاق المرسل الافتراضي* (موثّق مسبقًا لدى المزوّد)، و*حد الإرسال اليومي لكل
موقع*، وإرشادات DNS التي يراها العملاء: *SPF include* و*DKIM selector* ونوع سجل DKIM وقيمته
(`{domain}` و`{domain_dashed}` تُستبدلان)، وسياسة DMARC وعنوان تقاريرها، وقيم Return-Path. يُنصح
بتفعيل *التحقق من تسجيل الدخول إلى SMTP عند ضبط المواقع*. الحفظ يعيد ضبط المرحّل في كل موقع يستخدمه.

!!! warning "SPF وDKIM وDMARC لنطاقك"
    يجب أن يكون لـ *نطاق المرسل الافتراضي* سجل SPF (include لمزوّدك)، وسجلات DKIM من المزوّد، وسجل
    DMARC مثل `v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com`، وإلا ذهب البريد إلى الرسائل
    المزعجة. الحد اليومي يُكتب في إعدادات الموقع للعلم فقط؛ طبّقه فعليًا لدى مزوّد المرحّل.

**العلامات التجارية (العلامة البيضاء).** **علامة تجارية جديدة** ← معرّف العلامة، العنوان، اللون
الأساسي، رابط الشعار، رابط الأيقونة، بريد الدعم، اسم المرسل وعنوانه، *نطاقات البوابة (واحد في كل
سطر)*، نص التذييل، *العلامة الافتراضية للمنصة*. أي طلب يأتي على نطاق بوابة يعرض تلك العلامة في لوحة
التحكم وصفحات التسجيل والدخول، والفرق التي تُنشأ عليه تحتفظ بها في رسائلها.

!!! warning "نطاقات البوابة لا تُوجَّه تلقائيًا"
    لكل نطاق بوابة: أنشئ سجل CNAME/A إلى لوحة التحكم، وأضف المضيف إلى موقع لوحة التحكم
    (`bench setup add-domain` أو `domains` في إعدادات الموقع) **وإلى** الوكيل العكسي مع شهادة. في
    التثبيت الشامل لوحة التحكم موقع عادي، فيكفي
    `nexaploy site add-domain <cp domain> <portal domain> --wait` لإضافة المسار والشهادة. يجب أن
    يكون *عنوان المرسل* للعلامة قابلًا للإرسال من حساب البريد الصادر للوحة التحكم نفسها.

### 5.5 إصدارات الوكيل (Agent releases)

1. ضع وسمًا في المستودع (مثل `v0.2.0`، راجع `scripts/release.sh`).
2. **إصدار جديد** ← الإصدار، القناة (stable / beta)، مرجع Git (الافتراضي `v<version>`)، ورابط
   المستودع اختياريًا، أو رابط Wheel مع SHA-256، وملاحظات الإصدار.
3. **نشر**. و**إلغاء النشر** يخفيه.
4. في **الوكلاء على الخوادم** اضغط **معاينة القديمة** ثم **ترقية كل الخوادم القديمة**، أو **ترقية**
   لخادم واحد.

على الخادم تبني المهمة `agent.upgrade` بيئة جديدة بجانب الحالية، وتفحصها، وتبدّلها، وتعيد تشغيل
الوحدتين بعد 10 ثوانٍ من إبلاغ المهمة بالنجاح. مراقب يعيد الإصدار السابق تلقائيًا إذا لم يستجب الوكيل
الجديد. البنشات والمواقع لا تُمس. تُعتبر الترقية *فاشلة* إذا لم تصل نبضة بالإصدار الجديد خلال مهلة
ترقية الوكيل. الاسترجاع اليدوي: **استرجاع إصدار الوكيل السابق** في صفحة الخادم، أو على الخادم
`sudo nexaploy-agent rollback`. التفاصيل في [ترقية الوكيل](../operating.md#agent-upgrades).

### 5.6 مراجعة المتجر (Marketplace review)

- **إدراجات بانتظار المراجعة**: اقرأ الإدراج، واكتب *ملاحظات للناشر*، ثم **موافقة** أو **رفض**
  (الملاحظات إلزامية عند الرفض). الموافقة تنشئ إصدارًا لكل إصدار Frappe من فروع `version-NN`.
- **إصدارات بانتظار التحقق أو فشل التحقق منها**: كل إصدار جديد يُبنى تجريبيًا (Frappe + التطبيقات
  المطلوبة + التطبيق) قبل أن يراه العملاء. **اختبار مجددًا** يعيد البناء، و**Override** ثم **تعيين
  الحالة** يحددها يدويًا (*Verified* / *Failed*).
- **المراجعات**: **إخفاء** مراجعة (يُطلب السبب) أو **إظهار** مجددًا.

قائمة فحص المراجع: المستودع **عام** (البناء يتم بلا بيانات اعتماد)، والتطبيق يعمل على الإصدارات
المولّدة، والوصف والشعار والصور مناسبة، والسعر معقول.

### 5.7 الفرق والخوادم (Teams & servers)

- **الفرق** (مع بحث): المواقع، الخوادم، **الرصيد**، *معفى من الفوترة*، *احتفاظ ممتد*، *مفعّل*.
  الأزرار: **إيقاف** / **رفع الإيقاف** (إيقاف كل مواقع الفريق لأسباب الفوترة)، و**الرصيد** (منح رصيد؛
  القيمة السالبة تسوية، والسبب يظهر في سجل رصيد الفريق).
- **كل الخوادم**: الفريق، الحالة، القرص، النبضة، إصدار الوكيل، وهل هو مضيف لوحة التحكم أو خادم
  بناء، إضافة إلى **تحديثات النظام المعلّقة** و**يلزم إعادة التشغيل**.

## 6. الخوادم: الصحة والتنظيف وتحديثات النظام

افتح خادمًا من **الخوادم**. تعرض الصفحة معرّف الخادم، والنوع، وآخر نبضة، و**إصدار الوكيل** (مع
**ترقية الوكيل** / **استرجاع إصدار الوكيل السابق**)، والخطة، و**معلومات الخادم** (المعالج، الذاكرة،
الأقراص، الحاويات)، والبنشات، وآخر المهام مع مخرجات كل خطوة. يصبح الخادم *غير متصل* بعد 5 دقائق بلا
نبضة.

### صحة الخادم

لكل خادم حالة صحية:

| الحالة | المعنى |
|---|---|
| **OK** | لا شيء مطلوب |
| **Warning** | شيء يحتاج انتباهًا قريبًا |
| **Critical** | تصرّف الآن (مثل قرص ممتلئ تقريبًا أو قاعدة بيانات متوقفة) |
| **Unknown** | لم يكتمل أي فحص بعد |
| **Offline** | لا توجد نبضة |

تحت الحالة قائمة بالمشكلات، ولكل منها تلميح لحلها. ما يُفحص: مساحة القرص وعدد inodes، والذاكرة،
والحمل، ووحدات systemd الفاشلة، والحاويات التي تعيد التشغيل أو غير السليمة، وقاعدة البيانات،
والشهادات، ومزامنة الوقت، وإعادة التشغيل المعلّقة، والوكيل القديم، والنسخ الاحتياطية القديمة. اضغط
**Run full check** للفحص فورًا بدل انتظار النبضة التالية.

في **نظرة عامة** لوحة **صحة الخوادم** للأسطول كله. الخادم الذي يصبح *Critical* يرسل إشعارًا (الحدث
`server_health_critical`)، وعند تعافيه إشعارًا آخر (`server_health_ok`). ويرى العملاء شارة الصحة على
خوادمهم.

### تنظيف مساحة القرص

زر **Clean up** في صفحة الخادم يحرر المساحة عبر الوكيل:

1. اختر الأهداف (كلها محددة افتراضيًا):

    | الهدف | ما الذي يُحذف |
    |---|---|
    | صور Docker غير المستخدمة | صور لا تستخدمها أي حاوية (صور البنشات القديمة) |
    | ذاكرة البناء المؤقتة | build cache الخاص بـ Docker |
    | الحاويات المتبقية | حاويات مؤقتة متوقفة |
    | سجلات الحاويات | السجلات الضخمة، مع ضبط تدوير السجلات |
    | سجلات البنشات والمواقع القديمة | السجلات المدوّرة |
    | النسخ الاحتياطية المحلية | فقط النسخ **المرفوعة بالفعل** إلى التخزين، وليس النسخة الوحيدة أبدًا |
    | سجل المهام | سجلات مهام الوكيل القديمة |
    | سجل النظام | مدخلات `journald` القديمة |
    | ذاكرة apt | الحزم المنزّلة |
    | الملفات المؤقتة | الملفات المؤقتة القديمة |

2. شغّل **تجربة بدون تنفيذ** (dry run) أولًا: تعرض المساحة التي سيحررها كل هدف.
3. نفّذ التنظيف.

ملفات المواقع وقواعد البيانات والشهادات والإعدادات **لا تُمس أبدًا**.

في منطقة الإدارة يمكنك ضبط **سياسة تنظيف أسبوعية** تلقائية، وتشغيل **Clean up all servers** دفعة
واحدة. وعندما يصبح القرص في حالة حرجة يعمل تنظيف آمن تلقائيًا.

### بطاقة تحديثات النظام

في صفحة كل خادم بطاقة **تحديثات النظام** (System updates):

| تعرض | المعنى |
|---|---|
| التحديثات المعلّقة | الحزم القابلة للترقية، وكم منها تحديثات **أمنية** |
| النواة | النواة **العاملة** وأحدث نواة **مثبتة** |
| **يلزم إعادة التشغيل** (Reboot required) | الخادم يحتاج إعادة تشغيل (مثل نواة جديدة) |
| آخر تحديث | متى عملت آخر مهمة تحديث |

الإجراءات:

1. **حدّث الآن** (Update now): اختر *كل التحديثات* أو *الأمنية فقط*، وسلوك إعادة التشغيل *أبدًا* أو
   *عند الحاجة*. تعمل المهمة على الخادم، وإذا احتاجت إعادة تشغيل واخترت *عند الحاجة* تُجدول إعادة
   التشغيل **بعد أن تبلّغ المهمة بالنجاح**.
2. **أعد التشغيل الآن** (Reboot now): يعيد تشغيل الخادم (ويُجدول أيضًا بعد إبلاغ المهمة بالنجاح).
3. **نافذة الصيانة** (Maintenance window): *مفعّلة*، *اليوم*، *الساعة (UTC)*، و*إعادة التشغيل
   تلقائيًا عند الحاجة*. تعمل التحديثات حينها مرة أسبوعيًا في هذه النافذة.
4. **التحديثات الأمنية التلقائية** (Automatic security updates): تفعّل `unattended-upgrades` على
   الخادم، ولا تعيد التشغيل من تلقاء نفسها أبدًا؛ أعد التشغيل في نافذة الصيانة أو بزر **أعد التشغيل
   الآن**.

من يستطيع استخدامها: مسؤولو المنصة على كل الخوادم، والعملاء (Owner/Admin في الفريق) على خوادم
BYOS الخاصة بهم.

!!! warning "إعادة تشغيل خادم التثبيت الشامل"
    في التثبيت الشامل، إعادة تشغيل الخادم تعيد تشغيل لوحة التحكم أيضًا، فتغيب لوحة التحكم بضع دقائق.
    تعود البنشات والمواقع وMariaDB والوكيل العكسي ولوحة التحكم تلقائيًا (سياسات Docker ووحدات systemd).

## 7. مسابير مراقبة التوفر

كل موقع نشط يحصل تلقائيًا على مراقب توفر افتراضي. الفحوص تعمل من المسبار المدمج (مجدول لوحة
التحكم). في التثبيت الشامل هو المضيف نفسه للمواقع، فيرى العملاء تحذيرًا. أضف مسبارًا خارجيًا على
خادم VPS صغير في منطقة أخرى:

1. المكتب ← **Uptime Probe** ← جديد: الاسم (مثل `fra-1`) والمنطقة. انسخ **الرمز** (يظهر مرة واحدة؛
   `rotate_token` يصدر رمزًا جديدًا).
2. على الـ VPS:

    ```bash
    curl -fsSL -o /opt/nexaploy-probe \
      https://<control-plane>/api/method/nexaploy.api.monitoring_probe.download_script
    NEXAPLOY_URL=https://<control-plane> NEXAPLOY_PROBE_TOKEN=<token> python3 /opt/nexaploy-probe --once
    ```

3. شغّله دائمًا عبر systemd (`/etc/systemd/system/nexaploy-probe.service`):

    ```ini
    [Service]
    Environment=NEXAPLOY_URL=https://cp.example.com NEXAPLOY_PROBE_TOKEN=...
    ExecStart=/usr/bin/python3 /opt/nexaploy-probe
    Restart=always
    DynamicUser=yes

    [Install]
    WantedBy=multi-user.target
    ```

    ثم `systemctl enable --now nexaploy-probe`. المسبار يحتاج اتصال HTTPS صادرًا فقط.

مع عدة مسابير لا يُعتبر المراقب *متوقفًا* إلا إذا اتفق النصاب (الافتراضي: الأغلبية). الفحص كل دقيقة
وأكثر من 3 مراقبين للموقع يحتاجان ميزة *المراقبة المتقدمة* (علامة على الفريق أو في خطة الموقع).

## 8. تذاكر الدعم

يفتح العملاء التذاكر من **الدعم**. فريق الدعم هم المستخدمون الذين لهم دور **Nexaploy Support** (أو
System Manager). في المكتب افتح **Support Ticket** واستخدم **Reply** (مع *Mark as Resolved* اختياريًا).
زمن أول رد المستهدف: عاجلة ساعة، مرتفعة 4 ساعات، عادية 12 ساعة، منخفضة 24 ساعة، ويُظهر النموذج إن كان
الرد مستحقًا أو متأخرًا. التذاكر المحلولة تُغلق تلقائيًا بعد 7 أيام. التذاكر الجديدة تُرسل بالبريد إلى
المسؤول عنها، وإلا إلى كل مستخدمي Nexaploy Support، وإلا إلى *بريد التنبيهات*.

## 9. منتجات SaaS والتسجيل الذاتي

لبيع "ERPNext بنقرة واحدة":

1. جهّز مجموعة بنش **مشتركة** (بلا فريق) وانشر بنشات على خوادم مستضافة بلا فريق.
2. المكتب ← **SaaS Product**: الاسم المختصر (slug)، العنوان، مجموعة الإصدار، التطبيقات، الخطة
   الافتراضية، أيام التجربة (14)، النطاق (الافتراضي: النطاق الجذري)، مفعّل.
3. شارك الرابط `https://<cp>/signup/<slug>`. يُدخل الزائر الاسم والبريد وعنوان الموقع وكلمة المرور،
   ويؤكد بريده، فيحصل على فريق وموقع على أقل بنش ازدحامًا.
4. عند انتهاء التجربة وعدم قدرة الفريق على الدفع يصله بريد، وبعد 3 أيام يُوقف الموقع. ويتحول
   تلقائيًا إلى اشتراك مدفوع عندما يصبح الفريق قادرًا على الدفع.

## 10. الناشرون والمستحقات

تنشر الفرق تطبيقاتها المخصصة من صفحة **الناشر**، وتحصل على حصة (الافتراضي **80 %**، تُضبط لكل ناشر في
المكتب) من إيرادات التطبيقات المدفوعة. تراجع أنت الإدراجات في **مراجعة المتجر**. تُنشأ المستحقات يوميًا
في *يوم الفوترة + 5 أيام* عن الشهر السابق (على أساس المدفوع فعليًا) كمستندات **Publisher Payout** بحالة
**Draft**. في المكتب: **Approve** ثم **Mark Paid** (مع مرجع التحويل البنكي أو PayPal). مستحقات طريقة
*Credits* تُضاف إلى رصيد الناشر المسبق.

## 11. المراقبة والتنبيهات

| التنبيه | القاعدة | من يستلمه |
|---|---|---|
| القرص ممتلئ تقريبًا | القرص > 85 % | الفريق + *بريد التنبيهات*، مرة كل 6 ساعات على الأكثر لكل خادم |
| الخادم غير متصل | لا نبضة منذ 5 دقائق | كما سبق |
| حاويات غير سليمة | حاوية متوقفة أو غير سليمة | كما سبق |
| صحة الخادم حرجة / عادت سليمة | تغيّر الحالة إلى *Critical* أو منها | قنوات الفريق |
| الموقع متوقف / المراقب متوقف | فتح حادثة توفر | قنوات الفريق |
| فشل مهمة، فشل النسخ الاحتياطي | المهام الظاهرة للعميل | قنوات الفريق |
| صدور فاتورة، فشل الدفع، إيقاف المواقع | الفوترة | أعضاء الفوترة |

تختار الفرق قنواتها (البريد، تيليجرام، واتساب، Slack، Discord، webhook) من **الإشعارات**. ويستلم
*بريد التنبيهات* تنبيهات البنية التحتية دائمًا.

## 12. العمليات اليومية

**كل يوم**

1. الإدارة ← **نظرة عامة**: لوحة **صحة الخوادم** (أي خادم *Critical* أو *Warning*)، والخوادم غير
   المتصلة، وتنبيهات القرص، و*المهام الفاشلة (24 ساعة)*، والتذاكر المتأخرة.
2. افتح كل مهمة فاشلة (رابط المكتب)، واقرأ الخطوة الفاشلة، وعالج السبب، ثم أعد المحاولة (راجع
   [حل المشكلات](#16)).
3. أجب على تذاكر الدعم قبل موعدها.

**كل أسبوع**

1. **كل الخوادم**: التحديثات المعلّقة و*يلزم إعادة التشغيل*؛ استخدم **حدّث الآن** أو اعتمد على
   **نافذة الصيانة**.
2. استهلاك القرص: نفّذ **Clean up** للخوادم التي يزداد استهلاكها، أو اعتمد على سياسة التنظيف الأسبوعية.
3. **الوكلاء القدامى**: انشر إصدارات الوكيل ووزّعها.
4. **مراجعة المتجر**: الإدراجات والإصدارات التي فشل التحقق منها.
5. تأكد أن النسخ تصل إلى الحاوية (Site Backups بحالة *Success*)، وجرّب استعادة موقع واحد كموقع جديد.

**كل شهر**

1. بعد *يوم الفوترة*: الفواتير المتأخرة والفرق الموقوفة.
2. في *يوم الفوترة + 5*: اعتمد مستحقات الناشرين وادفعها.

## 13. ترقية المنصة نفسها

| ماذا | كيف |
|---|---|
| الوكيل | إصدارات الوكيل (القسم 5.5) |
| بنية الخادم (ملفات compose للوكيل العكسي وقاعدة البيانات، ووحدات systemd، والنظام) | أعد تشغيل `install.sh` على الخادم (يحتفظ بالأسرار)؛ والنظام عبر **حدّث الآن** |
| لوحة التحكم المستضافة | `cd ~/frappe-bench && bench update --apps nexaploy` أو `git pull` داخل التطبيق ثم `bench --site <cp> migrate` وإعادة التشغيل |
| لوحة التحكم في التثبيت الشامل | **Update control plane** في منطقة الإدارة، أو `sudo nexaploy controlplane update [--image IMG]` على الخادم |
| بنشات العملاء | انشر صورة جديدة لمجموعة البنش، و**تحديث آمن** لكل موقع |

ينفّذ **Update control plane** (في التثبيت الشامل) هذه الخطوات: نسخة احتياطية من لوحة التحكم ← سحب
الصورة الجديدة ← تبديل بنش لوحة التحكم إليها ← `migrate` ← فحص الصحة. إذا فشل فحص الصحة يعود إلى
الصورة السابقة تلقائيًا. ومن سطر الأوامر:

```bash
sudo nexaploy controlplane update                      # أحدث صورة
sudo nexaploy controlplane update --image ghcr.io/a7733mai/nexaploy-control-plane:<version>
```

تغيب لوحة التحكم لحظات أثناء التبديل، والمواقع تبقى تعمل.

!!! warning
    اقرأ `CHANGELOG.md` قبل أي ترقية. وفي لوحة التحكم المستضافة خذ نسخة احتياطية أولًا (القسم التالي).

## 14. النسخ الاحتياطي للوحة التحكم

- **التثبيت الشامل**: مهمة يومية تأخذ نسخة من موقع لوحة التحكم عبر الوكيل، وتُرفع بعد ضبط تخزين النسخ
  للمنصة. نسخة يدوية:

    ```bash
    sudo nexaploy controlplane backup --to /root/cp-backup     # نسخة كاملة للوحة التحكم في مجلد
    sudo nexaploy site backup cloud.example.com --wait         # الشيء نفسه كنسخة موقع عادية
    sudo nexaploy site backups cloud.example.com
    ```

    انسخ المجلد خارج الخادم (مثلًا `scp` أو `rclone`). هذا ما يحتاجه
    `install.sh --restore-control-plane`.

- **لوحة التحكم المستضافة**: استخدم نسخ Frappe العادية على بنش لوحة التحكم، مثل مهمة cron تنفّذ
  `bench --site cp.example.com backup --with-files`، وانسخ الملفات خارج الخادم.
- احتفظ كذلك بمجلد `/opt/nexaploy/config/` لكل خادم (رمز الوكيل، كلمة مرور root لقاعدة البيانات) في
  مدير كلمات مرور أو خزنة؛ فهو ليس ضمن نسخ المواقع.

## 15. خطة التعافي من الكوارث

!!! warning "تدرّب أولًا"
    نفّذ هذه الخطوات على خادم تجريبي قبل أن تحتاجها فعلًا.

**موقع عميل معطّل أو حُذفت بيانات منه**

1. الموقع ← **النسخ الاحتياطية ← الاستعادة إلى نقطة زمنية** إلى *موقع جديد*، قارن، ثم استعد في المكان
   نفسه إن لزم؛ أو **النسخ الاحتياطية ← استعادة…** مع *قاعدة البيانات فقط* / *الملفات فقط*.

**فقدان خادم** (يتطلب تخزين نسخ في حاوية)

1. ثبّت خادمًا جديدًا وسجّله (للفريق نفسه).
2. انشر مجموعات البنش نفسها عليه (**نشر على خادم**).
3. لكل موقع: **النسخ الاحتياطية ← استعادة… ← استعادة كموقع جديد** على البنش الجديد (يجب أن يقرأ خادم
   البنش التخزين نفسه)، أو اطلب ذلك من الفريق.
4. وجّه DNS لكل النطاقات إلى الخادم الجديد؛ الشهادات تصدر تلقائيًا.
5. أرشف الخادم القديم. أرشيف سجلات binlog يتيح نقطة استعادة بفارق 15 دقيقة تقريبًا لقواعد البيانات.

**فقدان لوحة التحكم المستضافة**

الخوادم تستمر في العمل: المواقع متاحة والوكلاء يعيدون المحاولة. استعد آخر نسخة من لوحة التحكم على بنش
Frappe جديد **بالنطاق نفسه** (`bench --site cp.example.com restore … --with-public-files …
--with-private-files …`) ثم `migrate`. رموز الخوادم موجودة في قاعدة البيانات المستعادة، فيعود الوكلاء
للاتصال تلقائيًا بمجرد أن يشير DNS إلى المضيف الجديد.

**نقل لوحة التحكم إلى خادم جديد، أو فقدان خادم التثبيت الشامل**

تحتاج نسخة احتياطية من لوحة التحكم (`nexaploy controlplane backup --to <dir>` أو النسخة اليومية في
الحاوية) منسوخة خارج الخادم القديم.

1. انسخ النسخة إلى الخادم الجديد.
2. ثبّت معها:

    ```bash
    curl -fsSL https://raw.githubusercontent.com/a7733mai/NexaPloy-/main/agent/install/install.sh \
      | sudo bash -s -- --with-control-plane cloud.example.com --acme-email ops@example.com \
          --restore-control-plane /root/cp-backup --skip-dns-check
    ```

    (`--skip-dns-check` لأن DNS ما زال يشير إلى الخادم القديم.)
3. غيّر سجل DNS لنطاق لوحة التحكم إلى الخادم الجديد. تصدر الشهادة بعد تغيّر DNS.
4. الخوادم الأخرى تستمر في العمل طوال الوقت وتعود للاتصال بلوحة التحكم تلقائيًا.
5. إذا ضاع خادم التثبيت الشامل القديم فقد ضاعت مواقع العملاء عليه أيضًا: استعدها من الحاوية على خادم
   كما في *فقدان خادم*.

## قائمة فحص الأمان

- `--acme-email` عنوان حقيقي؛ المنفذان 80/443 مفتوحان وكل ما عداهما مغلق (لا SSH من الإنترنت، أو
  SSH بالمفاتيح فقط).
- تغيير كلمة مرور Administrator بعد التثبيت، والحفاظ على سرية `control-plane.env` (صلاحيات 600).
- المصادقة الثنائية لكل مستخدمي فريق التشغيل (System Settings)، وللعملاء خيار *فرض المصادقة الثنائية*
  على الفرق التي تحتاجه.
- تخزين النسخ الاحتياطية **خارج الخادم**، مع تجارب استعادة منتظمة.
- تحديثات النظام أسبوعيًا (**نافذة الصيانة** + **التحديثات الأمنية التلقائية**).
- كل الخوادم بحالة صحة **OK**، وإشعارات `server_health_critical` تصلك.
- الوكلاء على آخر إصدار مستقر.
- أسرار webhook لـ Stripe/Paymob مضبوطة، وروابط webhook كلها HTTPS.
- SPF/DKIM/DMARC لنطاق مرسل المرحّل.
- عدد قليل فقط من المستخدمين لهم دور System Manager؛ راجع **آخر تغييرات المنصة** ونشاط الفرق.
- مراجعة تطبيقات المتجر (مستودع عام وكود معقول) قبل الموافقة.
- مسبار مراقبة خارجي في منطقة أخرى.

المزيد في [نموذج الأمان](../security.md).

## 16. حل المشكلات { #16 }

### أين تبحث

```bash
nexaploy ping                                   # هل واجهة الوكيل تعمل؟ وما الإصدار؟
nexaploy jobs --status failure                  # المهام الفاشلة على هذا الخادم
nexaploy jobs <job id>                          # كل خطوة بمخرجاتها والخطأ
journalctl -u nexaploy-agent-worker -n 200 -f   # المهام والنبضة والاستطلاع
journalctl -u nexaploy-agent-api -n 200         # الواجهة البرمجية المحلية
docker ps --format '{{.Names}}\t{{.Status}}'    # nexaploy-db و nexaploy-traefik و <bench>-*
docker logs nexaploy-traefik --tail 100         # TLS والتوجيه
docker logs nexaploy-db --tail 100              # MariaDB
cat /var/log/nexaploy-install.log               # الخوادم المجهزة بـ cloud-init أو الصور
```

### مشكلات شائعة

| العَرَض | السبب والحل |
|---|---|
| `port 80 is already in use` أثناء التثبيت | خادم ويب آخر (nginx أو Apache أو Caddy) يستمع. أوقفه أو استخدم خادمًا جديدًا. |
| المتصفح يعرض شهادة Traefik الافتراضية، وحالة TLS *الشهادة الافتراضية* | DNS لا يشير إلى هذا الخادم، أو المنفذ 80 محجوب، أو `--acme-email` ما زال `admin@example.com`، أو حد معدل Let's Encrypt. ابحث عن `acme` في `docker logs nexaploy-traefik`. يجب أن تكون صلاحيات `acme.json` ‏600 ومالكه 3100. |
| مواقع v16 لا تتصل بقاعدة البيانات، وأخطاء TLS/SSL في `bench new-site` | عميل MariaDB 11.8 في v16 يشترط TLS. أعد تشغيل `install.sh` (تصبح القاعدة `mariadb:11.8`، وبيانات 10.6 تُرقّى في مكانها). إن ضبطت `MARIADB_IMAGE` فاستخدم 11.4 أو أحدث. |
| القرص ممتلئ وMariaDB متوقف | **Clean up** في صفحة الخادم (بتجربة بدون تنفيذ أولًا)؛ أو يدويًا: `df -h /opt/nexaploy` و`docker system df` و`docker image prune`؛ قلّل الاحتفاظ المحلي واضبط تخزينًا خارجيًا. |
| صحة الخادم *Critical* | افتح صفحة الخادم؛ لكل مشكلة تلميح. عالجها ثم اضغط **Run full check**. |
| فشل فحص نطاق لوحة التحكم أثناء التثبيت | النطاق لا يشير إلى هذا الخادم بعد: صحّح سجل DNS وانتظر، أو استخدم `--skip-dns-check`. |
| الخادم *غير متصل* | `systemctl status nexaploy-agent-worker`؛ ظهور `401` في السجل يعني رمزًا خاطئًا (أرشفة أو تدوير): أعد التسجيل برمز جديد مع `--force-register`. |
| فشلت مهمة | المهام المحلية: عالج السبب ثم `nexaploy retry <job id> --wait` (تُتخطى الخطوات الناجحة). مهام لوحة التحكم: المكتب ← Agent Job ← **Retry**. النقل الفاشل يكمل عند إعادة مهمته الفاشلة. |
| لا يمكن سحب الصورة على خادم آخر | اضبط *السجل* (الميزات والأسعار ← النسخ الاحتياطية والوكلاء). |
| فشلت ترقية الوكيل | المراقب يعيد الإصدار السابق بعد ~3 دقائق؛ يدويًا `sudo nexaploy-agent rollback`. |
| الخادم يبقى على *يلزم إعادة التشغيل* | استخدم **أعد التشغيل الآن**، أو دع **نافذة الصيانة** تعيد تشغيله. |

### ملاحظات Frappe v16

- مجموعات البنش الجديدة تستخدم v16 افتراضيًا (Python 3.14 وNode 24).
- الخيار `--no-mariadb-socket` أصبح قديمًا؛ يستخدم الوكيل `--mariadb-user-host-login-scope=%` ولا يعود
  للخيار القديم إلا مع v14.
- صور v16 الرسمية تضع الأصول في `./assets` وتعمل بالمستخدم `1000:0`؛ أما صور الإنتاج من `image-builder/`
  فتتبع عقد Nexaploy (UID 3113).

## 17. مرجع سطر الأوامر

الأمران مثبتان في `/usr/local/bin` على كل خادم. شغّلهما بصلاحيات root.

### `nexaploy` (يتعامل مع واجهة الوكيل المحلية)

الخيارات العامة: `--url` و`--token` (أو `NEXAPLOY_URL` / `NEXAPLOY_TOKEN`) و`--config/-c` و`--json`.
الأوامر التي تغيّر شيئًا تطبع رقم المهمة، و`--wait/-w` يتابع المهمة حتى تنتهي.

| الأمر | الغرض |
|---|---|
| `nexaploy ping` | إصدار الوكيل ومعرّف الخادم |
| `nexaploy server` | معلومات الخادم |
| `nexaploy jobs [ID] [--status S] [--kind K] [--limit N] [--wait]` | سرد المهام / عرض مهمة أو متابعتها |
| `nexaploy cancel ID` | إلغاء مهمة في الطابور |
| `nexaploy retry ID [--wait]` | إعادة مهمة فاشلة من الخطوة الفاشلة |
| `nexaploy build --tag T --major 14\|15\|16 --apps-json FILE [--frappe-branch B] [--push]` | بناء صورة بنش |
| `nexaploy bench list` | البنشات |
| `nexaploy bench create NAME --image TAG [-e KEY=VAL] [--apps-json F]` | إنشاء بنش |
| `nexaploy bench update NAME --image TAG` | صورة جديدة + ترحيل كل المواقع |
| `nexaploy bench start\|stop\|restart NAME` | التحكم في بنش |
| `nexaploy bench remove NAME [--force]` | حذف بنش |
| `nexaploy site list [--bench B]` | المواقع |
| `nexaploy site create SITE --bench B [-a APP]…` | موقع جديد (يسأل عن كلمة مرور المسؤول، أو `NEXAPLOY_ADMIN_PASSWORD`) |
| `nexaploy site install-app SITE APP` / `uninstall-app SITE APP` | التطبيقات |
| `nexaploy site add-domain SITE DOMAIN` / `remove-domain SITE DOMAIN` | النطاقات |
| `nexaploy site backup SITE [--no-files] [--no-upload]` | نسخة احتياطية |
| `nexaploy site backups SITE` | النسخ المحلية والبعيدة |
| `nexaploy site restore SITE --backup-id TS \| --remote-path PATH [--bench B]` | استعادة |
| `nexaploy site migrate SITE` | `bench migrate` |
| `nexaploy site set-config SITE KEY VALUE [-p]` | إعداد الموقع (`-p` يقرأ القيمة كـ JSON) |
| `nexaploy site drop SITE [--skip-backup] [-y]` | حذف موقع (بعد نسخة احتياطية) |
| `nexaploy controlplane update [--image IMG]` | التثبيت الشامل: تحديث لوحة التحكم (نسخة، تبديل، ترحيل، فحص صحة، رجوع عند الفشل) |
| `nexaploy controlplane backup --to DIR` | التثبيت الشامل: نسخة احتياطية للوحة التحكم في مجلد |

### `nexaploy-agent` (الخدمات والصيانة)

| الأمر | الغرض |
|---|---|
| `nexaploy-agent api [--host] [--port]` | الواجهة المحلية (وحدة systemd ‏`nexaploy-agent-api`) |
| `nexaploy-agent worker` | منفّذ المهام والنبضة والاستطلاع (`nexaploy-agent-worker`) |
| `nexaploy-agent register --control-plane URL --token T [--site-name D]` | التسجيل في لوحة تحكم |
| `nexaploy-agent version` | طباعة الإصدار |
| `nexaploy-agent upgrade --version X [--ref R] [--repo-url U] [--wheel-url W --wheel-sha256 H] [--no-restart]` | جدولة ترقية محلية للوكيل (للخوادم المستقلة) |
| `nexaploy-agent rollback [--no-restart]` | إعادة الإصدار السابق للوكيل |

إذا لم يعمل حتى سطر الأوامر الجديد:
`sudo /opt/nexaploy/agent/.venv.prev/bin/python -m nexaploy_agent.agent_cli rollback`.
